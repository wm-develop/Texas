# 阶段 3：上线准备计划

- 状态：开发中（3.1/3.2 单实例链路及真实 PostgreSQL 验收已完成；持久化文字禁言治理及生产更新流程已完成，Redis、多实例、举报与运行保障继续开发）
- 前置条件：阶段 2 功能与自动化验收已完成
- 目标：把当前单机、进程内仓储的封闭测试 MVP，提升为可部署、可恢复、可观测、可治理的熟人牌局服务。

## 1. 范围与原则

- 仍然只服务熟人私人牌局，不增加公开匹配、排行榜、现金交易或互联网推广能力。
- 牌局状态继续由 Go 服务端权威裁决，客户端不得成为事实来源。
- 游戏、文字聊天和 RTC 保持独立故障域；任一辅助能力故障时，牌局核心流程应能继续或明确恢复。
- 先解决数据安全和单实例可靠性，再进入多实例、压测和发布自动化。
- 所有生产配置通过环境变量或密钥服务注入，仓库只保留无敏感值的模板。

## 2. 工作分解

### 3.1 数据持久化与迁移

- [x] 建立 PostgreSQL 迁移框架和版本化 SQL（嵌入式 up/down、事务、校验和、并发迁移锁和独立命令已完成；真实数据库集成测试由 `TEST_DATABASE_URL` 启用）。
- [x] 实现用户、密码摘要、Access/Refresh 会话的 PostgreSQL 仓储；注册用户与初始化零余额钱包在同一事务完成。
- [x] 持久化用户、密码摘要、刷新会话、房间、成员和座位。
- [x] 持久化手牌概要、参与者、行动、结算结果和追加式筹码账本。
- [x] 持久化文字聊天、管理员禁言状态及相应的不可修改审计事件。
- [ ] 持久化举报、语音加入/退出元数据。
- [x] 为现有账号、房间、历史、聊天和账本接口实现 PostgreSQL 仓储，保留内存实现用于测试。
- [x] 关键写入使用事务；以 `handId`、`actionId` 和 `clientMessageId` 建立唯一约束。
- [x] 增加迁移升级、回滚、空库初始化和迁移漂移拒绝测试；真实库集成用例由 `TEST_DATABASE_URL` 启用。

验收：服务重启后账号、会话、最近牌局和账本保持一致；重复结算不会产生重复流水。

### 3.2 娱乐筹码钱包、带入与补码

- [x] 每个账户建立可持久化的娱乐筹码余额，并在大厅明确展示。
- [x] 提供虚拟充值页面：玩家可输入任意正整数筹码，确认后立即成功；不接入支付平台，不展示金额、订单或任何现实货币概念。
- [x] 虚拟充值生成不可变的 `virtual_top_up` 账本流水，并以请求 ID 保证重复点击不会重复增发。
- [x] 创建房间时由房主自定义小盲、大盲和单个玩家的最大带入；创建后本房间内不可修改。
- [x] 加入房间时弹出带入窗口，玩家自主选择从账户钱包转入牌桌的数量。
- [x] 带入必须为正整数、不超过账户可用余额，且资金操作后玩家牌桌筹码不得超过房间最大带入；正常牌局赢得的筹码允许高于该值，但不能继续补码。
- [x] 每手结束后为所有仍在房间的玩家提供“补码”按钮，仅允许在两手之间操作。
- [x] 补码窗口显示账户余额、当前牌桌筹码、最大带入和本次最多可补数量。
- [x] 玩家本手输光时自动弹出补码窗口；未完成补码则保持坐下但不参与下一手。
- [x] 主动离桌或房间关闭时，将玩家剩余牌桌筹码幂等退回账户钱包；被移出流程待管理功能实现。
- [x] 带入、补码、退回和牌局结算共用追加式双边账本；钱包与牌桌筹码的转移不能凭空增减总量，只有虚拟充值允许增发。
- [x] 大厅提供最近娱乐筹码流水，可核对充值、带入、补码、牌局结算和离桌返还后的钱包/牌桌余额。
- [x] 将余额扣减、牌桌加码和账本写入放在同一数据库事务中，并锁定账户/座位防止并发超额带入。
- [x] 客户端覆盖大厅余额与充值、建房盲注/最大带入、入房带入、主动补码和输光自动补码五条流程。

验收：并发点击、网络重试、断线重连和服务重启均不会复制或丢失筹码；带入或补码操作不能使牌桌筹码超过房间最大带入，牌局赢取筹码不受该资金上限截断。

### 3.3 Redis 与多实例牌桌路由

- [ ] 使用 Redis 保存在线状态、房间到服务实例的路由、短期幂等结果和必要的事件游标。
- [ ] 设计牌桌单写者租约，确保同一牌桌同一时刻只有一个权威执行实例。
- [ ] 实现实例失联后的租约过期、牌桌恢复和客户端重连路由。
- [ ] 明确 Redis 不可用时的降级策略，禁止出现双写牌桌。

验收：至少两个游戏服务实例运行时，玩家仍能加入同一牌桌；单实例退出后可恢复且筹码守恒。

### 3.4 会话、安全与配置

- [x] Access Token 缩短为可配置的短期凭证，客户端在 REST、WebSocket 重连和 RTC 鉴权前自动轮换 Refresh Token；支持会话撤销和注销。
- [ ] 登录、注册、建房、入房、WebSocket、聊天和 TRTC 凭证分别限流。
- [ ] 配置允许来源、请求体上限、连接上限和可信代理规则。
- [ ] 生产环境强制 HTTPS/WSS，设置安全响应头并隐藏内部错误。
- [ ] TRTC UserSig、数据库口令和签名材料接入部署平台密钥管理。
- [ ] 增加账号注销、数据清理和隐私提示流程。
- [ ] 进行依赖、密钥泄漏和常见 Web/API 风险扫描。

验收：会话撤销立即生效；未授权用户不能访问房间、历史或 RTC；仓库扫描不包含真实密钥。

### 3.5 管理、举报与聊天治理

- [ ] 增加玩家举报入口和必要的上下文采集，不记录音频内容。
- [x] 建立账号与文字禁言管理 API/后台：查询用户、封禁账号、禁言/解除禁言、房间移出和注册开关。
- [x] 服务端持久化禁言状态，并对已连接的 WebSocket 立即生效。
- [ ] 增加举报处置和审计记录查询界面。
- [x] 已有管理操作要求独立管理员权限、客户端二次确认和不可修改的审计事件。

验收：被禁言用户不能发送文字消息；被封禁用户不能登录；所有管理动作可以追溯。

### 3.6 可观测性与运行保障

- [ ] 结构化日志统一请求 ID、用户 ID、房间 ID、手牌 ID 和错误码，避免记录底牌和密钥。
- [ ] 暴露健康、就绪和指标端点（`/healthz`、`/readyz` 已完成，指标待实现）。
- [ ] 监控连接数、牌桌数、动作延迟、错误率、重连率、RTC 凭证失败和账本异常。
- [ ] 建立关键告警、日志保留和问题定位手册。
- [ ] 实现优雅停机：停止接收新牌桌，等待或迁移进行中的牌桌。

验收：可从监控发现服务异常，并通过请求/牌桌/手牌标识定位问题而不泄漏隐藏信息。

### 3.7 备份、恢复与数据校验

- [ ] 制定 PostgreSQL 自动备份、保留周期和加密策略。
- [ ] 在隔离环境执行恢复演练并记录 RPO/RTO。
- [ ] 编写账本与手牌结算对账任务，发现不守恒时报警而非自动改账。
- [ ] 验证数据库升级失败后的恢复路径。

验收：从备份恢复后，账号、手牌和账本数量及校验结果一致。

### 3.8 弱网、负载和稳定性

- [ ] 覆盖延迟、抖动、丢包、短时断网、网络切换和重复消息。
- [ ] 压测注册/登录、入房、WebSocket 广播、聊天和历史查询。
- [ ] 进行 10 人桌、多桌并发及 RTC 长时间稳定性测试。
- [ ] 连续运行至少 24 小时，期间注入数据库、Redis、RTC 和单实例故障。
- [ ] 保留筹码守恒、无卡死手牌、无跨房消息和无隐藏牌泄漏的自动断言。

验收：24 小时无不可恢复的牌局状态错误；辅助服务故障符合降级设计。

### 3.9 CI、发布与版本治理

- [ ] 配置 GitHub Actions：Go 格式/静态检查/测试、Flutter 静态检查/测试和密钥扫描。
- [x] 为服务端创建可复现的容器构建和本地 PostgreSQL/Redis 开发编排。
- [x] 建立数据库迁移、服务部署和回滚流程，并形成可重复执行的生产更新手册。
- [ ] 建立客户端版本号、最低兼容协议和强制升级策略。
- [ ] 生成 Web 部署包、Windows 分发包、Android 签名包和 HarmonyOS 签名包。
- [ ] 为每个平台建立发布前核心流程冒烟清单，不在 CI 中保存签名私钥明文。

验收：从干净环境可重复完成检查、构建、部署和回滚；旧客户端收到明确的兼容提示。

## 3. 推荐实施顺序

1. PostgreSQL 迁移、账户钱包和追加式账本。
2. 虚拟充值、房间盲注/最大带入、入房带入和两手之间补码。
3. 会话撤销、持久化禁言与配置安全。
4. Redis 路由、单写者租约和多实例恢复。
5. 日志、指标、告警和账本对账。
6. 举报、管理和审计。
7. 备份恢复、弱网、负载与 24 小时稳定性。
8. CI、容器化、版本治理和四端发布流程。

前四项完成前不进行公网部署；备份恢复和 24 小时验收通过前不向熟人测试群分发长期运行版本。

## 4. 阶段退出标准

- PostgreSQL/Redis 故障边界明确，生产数据可备份、恢复和对账。
- 账户虚拟充值、带入、补码、退回和牌局结算均可审计；任何带入或补码均不能把牌桌筹码提高到房间最大带入以上。
- 两个服务实例可承载牌桌，单实例退出不会产生双写或筹码错误。
- 游戏、文字聊天和语音任一服务故障时，其余功能按设计继续或恢复。
- 10 人桌、多桌并发和 24 小时测试无状态不一致、卡死牌局或筹码不守恒。
- 管理、禁言、封禁、举报和审计形成完整闭环。
- Web、Windows、Android、HarmonyOS 完成签名构建及发布前实机冒烟。
- CI 能阻止测试失败、格式错误和疑似密钥泄漏进入主分支。

## 5. 暂不纳入阶段 3

- 公开大厅、随机匹配和陌生人社交。
- 现金、付费充值、提现、兑换或任何可交易筹码。
- 排行榜、赛事系统、俱乐部运营和商业化。
- 牌局录像和语音录制。
- iOS 正式签名与 App Store 发布；在具备证书和设备后单独评估。
