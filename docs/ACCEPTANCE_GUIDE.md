# 验收指南：稳定性、弱网与发布冒烟

本文覆盖三件发布前必须做、且**只能在真实环境完成**的事：

1. [24 小时稳定性观测](#1-24-小时稳定性观测)——服务端跑一整天不泄漏、不静默重启。
2. [弱网与断线验收](#2-弱网与断线验收)——断线重连、补发、语音与牌局互不牵连。
3. [发布冒烟清单](#3-发布冒烟清单)——四端各跑一遍，重点覆盖历史上真机才暴露的问题。

自动化测试（`go test ./...`、`flutter test`、CI）只能证明逻辑分支正确，证明不了「一整天不泄漏」和「电梯里断网能回来」。三项各自的记录模板在文末，每次发布把填好的记录附在 Release 说明里。

## 1. 24 小时稳定性观测

### 1.1 观测什么

[`deploy/monitor/texas-soak.sh`](../deploy/monitor/texas-soak.sh) 周期抓取 `/metrics` 与 `/readyz`，写成 CSV，结束时给出判定。看的是**趋势**而不是瞬时值：

| 指标 | 异常形态 | 说明 |
|---|---|---|
| `texas_goroutines` | 连接回落后不回落 | 每连接的协程没退出，最典型的泄漏 |
| `texas_memory_heap_bytes` | 单调上涨不回落 | 有对象被长期持有 |
| `texas_process_start_time_seconds` | 发生变化 | 容器静默重启，之前的趋势作废 |
| `texas_snapshot_broadcast_failures_total` | 大于 0 | 有整桌收不到快照 |
| `texas_websocket_connections_active` | 无人在线却不为 0 | 连接对象没释放 |
| `/readyz` | 任何一次失败 | 期间出现过不可用 |

判定阈值取「相对观测期内最低点」的增长，而不是相对起点：服务刚启动时基数低，用起点会把正常预热误判成泄漏。默认 goroutine +200、堆内存 +256 MB，可用 `TEXAS_SOAK_GOROUTINE_GROWTH`、`TEXAS_SOAK_HEAP_GROWTH_MB` 调整。

### 1.2 准备

`/metrics` 需要令牌，写入 `/opt/texas/soak.env`（与游戏服务 `.env` 中的 `METRICS_TOKEN` 一致）：

```bash
sudo install -m 600 /dev/null /opt/texas/soak.env
```

用编辑器写入一行 `TEXAS_METRICS_TOKEN=你的令牌`。**不要**把令牌写进命令行，它会留在 shell 历史里。

同步脚本并赋予执行权限：

```bash
sudo install -m 755 deploy/monitor/texas-soak.sh /opt/texas/bin/texas-soak.sh
```

### 1.3 运行

观测要跑满 24 小时，必须放进 `tmux` 或 `nohup`，SSH 断开不能中断：

```bash
tmux new -s soak '/opt/texas/bin/texas-soak.sh 2>&1 | tee /opt/texas/soak/last-run.log'
```

先用短时长确认链路通，再开正式一轮：

```bash
/opt/texas/bin/texas-soak.sh --hours 0.05 --interval 30
```

脚本启动时会先抓一次 `/metrics` 核对指标名。服务端改名而脚本没跟上时，缺失项会被静默记成 0、整轮观测失去意义，因此这里直接快速失败。

中途 `Ctrl-C` 也会先输出判定再退出，退出码即判定结果（0 通过、1 不通过、2 配置错误），可以直接接进自动化。对已有 CSV 重新判定：

```bash
/opt/texas/bin/texas-soak.sh --report /opt/texas/soak/soak-20260902-000000.csv
```

### 1.4 观测期间要有真实负载

空转 24 小时证明不了什么——泄漏往往发生在连接建立与销毁的路径上。观测期内至少制造以下负载，并记录大致时间点：

- 完整打完 **20 手以上**，覆盖 2 人和 6 人两种桌型。
- 反复进出牌桌 **10 次以上**（含弃牌后离开、结算后离开）。
- 反复加入/退出语音 **10 次以上**。
- 制造 **3 次以上**客户端断线重连（直接杀掉 App 或断网）。
- 触发一次限流（例如连续输错密码），确认计数上升且服务未受影响。

结束时让所有人离线，等一个采样周期再看：**连接归零后 goroutine 应当回落到接近开局水平**。这一步是整轮观测里最关键的判断。

### 1.5 判定不通过怎么办

| 判定 | 先查什么 |
|---|---|
| 进程重启过 | `docker inspect texas-game-server --format '{{.RestartCount}} {{.State.OOMKilled}}'`、`docker logs --since 24h texas-game-server` |
| 出现过不可用 | 健康巡检是否已告警；数据库容器状态；同时段服务日志 |
| 广播失败 | 服务日志中的 broadcast 记录，确认是整桌失败还是单连接失败 |
| goroutine 泄漏 | 与连接数曲线对照；重点看断线重连和离桌路径 |
| 堆内存增长 | 与牌局数对照；确认是否为聊天历史、事件缓冲等有上限的缓存 |

## 2. 弱网与断线验收

### 2.1 客户端的既有机制

验收是在核对这些机制是否按设计工作，不是随便断网看看：

- 心跳每 **25 秒**一次；**75 秒**收不到任何服务端消息即判定断线并重连。
- 重连退避 **1 → 2 → 4 → 8 秒**封顶。
- 重连时带上 `lastSequence`；服务端在 `table.joined` 回 `resumedFromSequence`、最近 50 条聊天和当前语音成员。
- 序号不连续时客户端置 `sequence_gap` 并请求快照，服务端回补发或整份快照。
- 动作被拒绝后客户端**总是**重新拉一次快照，避免动作栏停留在过期版本。
- 结算后自动准备倒计时 **10 秒**（发两次 **15 秒**）；短暂断线不等同于取消准备。
- 语音走 TRTC，与牌局 WebSocket 相互独立：**退出语音不会断开牌局，牌局断线也不应踢掉语音**。

### 2.2 如何制造弱网

| 平台 | 方法 |
|---|---|
| Web | Chrome DevTools → Network → 选 `Offline` 或 `Slow 3G`；WebSocket 需用 Offline 才会真正断开 |
| Android / HarmonyOS | 下拉通知栏开关飞行模式；或设置里禁用 Wi-Fi 与蜂窝 |
| Windows | `Disable-NetAdapter -Name "Wi-Fi" -Confirm:$false`，恢复用 `Enable-NetAdapter` |

服务端侧的丢包模拟（`tc netem`）不必做：本项目要验证的是客户端恢复路径，直接断网更接近真实场景（电梯、地铁、切后台）。

### 2.3 验收场景

每条都记录「实际现象」和「是否通过」。**加粗**部分是判定依据。

**A. 轮到自己时断线 5 秒**
断网 5 秒后恢复。预期：连接状态条显示重连并自行恢复；**行动截止时间由服务端权威给出，不因断线延长**；若期间超时，服务端按规则自动处理（过牌或弃牌），恢复后快照与之一致，客户端不出现「本地还能操作」的错觉。

**B. 轮到自己时断线 90 秒**
超过心跳判定阈值。预期：客户端进入重连；恢复后**手牌、底池、公共牌、筹码与其他玩家看到的完全一致**；这一手若已结束，直接进入下一手的准备状态。

**C. 结算瞬间断线**
在摊牌动画期间断网 20 秒。预期：恢复后**筹码结算结果正确且只结算一次**；自动准备倒计时按服务端剩余时间显示，不从头开始。

**D. 断线跨越自动准备倒计时**
结算后立刻断网 20 秒（超过 10 秒倒计时）。预期：**短暂断线不等同于主动取消准备**，恢复后状态与服务端一致；主动发送取消准备才会退出本轮。

**E. 后台驻留后回到前台**
把 App 切到后台 5 分钟再回来（手机上最常见）。预期：回到前台后自动重连并拉到最新快照，**不需要手动退出重进房间**。

**F. 弱网下连续操作**
`Slow 3G` 下连续点击加注、过牌。预期：**同一动作不会被提交两次**（动作有唯一 `actionId` 与幂等缓存）；被拒绝时给出中文提示并自动重新同步。

**G. 语音与牌局互不牵连**
- 牌局 WebSocket 断线时，**语音应继续通话**。
- 主动退出语音时，**牌局不断线、不影响行动**。
- 语音断线重连后，其他人看到的开麦状态与实际一致。

**H. 中途加入 + 断线**
牌局进行中加入房间成为「待入座」，随即断线重连。预期：恢复后仍是待入座、**收不到任何底牌**，本手结算后正常获得座位。

**I. 弃牌后离开 + 断线**
弃牌后点离开，立刻断网。预期：恢复后**筹码返还只发生一次**，钱包与流水对得上。

**I-3. 倒计时到点的瞬间离开（服务端必测）**
三人以上，一手结算后盯着 10 秒自动准备倒计时，在数字跳到 0 的那一瞬间点离开，多试几次。预期：其余人的下一手照常结算并入账（「最近牌局」里能看到），没有任何人看到「牌桌操作失败」；离开者的筹码正常退回。反例（旧版本）：之后每一手结束时最后行动的人看到 `table_chips_not_conserved`，其他人看到「他点了弃牌没反应」，房间只能重开。同时验证：若确实出现结算失败，服务端日志里有 `hand settlement was not persisted`，全桌都收到了结算后的快照，下一手在补做成功前开不了。

**I-2. 弃牌后中途离开、反复进出同一房间（服务端必测，必须接 PostgreSQL）**
三人以上的牌局里，在**已经下过注**（例如盲注位）的那一手弃牌后立刻离开。预期：本手照常结算，其他人不会看到「牌桌操作失败」；结算后钱包收到的是**弃牌后的筹码**（带入减去这一手已下的注），「最近牌局」里有这一手且包含离开者。随后重新进入同一房间再离开（手间），预期**第二次也退还**；「本房间战绩」的累计带入、累计返还跨两次进出延续。离开后、那一手还没打完时：重启应用应停在大厅而不是被送回牌桌；此时创建房间提示「你刚离开的那一手还没打完」；输入原房间码加入则直接回到原座位，筹码不变、不重复扣带入。用下面的查询核对流水——每次离开都应有一条 `cash_out`：
`SELECT created_at, reason, wallet_delta, table_delta FROM bankroll_entries WHERE user_id = '<用户ID>' AND room_id = '<房间ID>' ORDER BY created_at;`

**I-5. 牌局回放（四端各走一遍；需要至少三个账号）**
打几手不同的牌：有人翻牌前全弃、打到摊牌、有人全下后发两次、有人超时、有人弃牌后离开。然后每个账号在「牌局记录」里展开这些手、点「回放这一手」。预期：
- 第一帧是发牌与盲注，之后每个动作一步，发翻牌/转牌/河牌各一步，最后是摊牌（如有）与结算；逐步前进、后退、拖动进度、播放与倍速都正常，放到最后自动停下。
- **自己的牌每一帧都在；别人的牌只在摊牌那一步之后出现；弃牌、没摊牌就结束的人的牌从头到尾都看不到。** 结算后自愿亮牌、私下看牌不会出现在回放里。
- 每一步的筹码与底池与当时牌桌上看到的一致，最后一步各人筹码与「牌局记录」里的结束筹码一致；超时的动作标「超时自动」；抽水的房间最后一步写明抽水。
- 手机横屏下牌桌与控件都完整可见；把「牌局记录」翻到第二页、第三页，没有重复和遗漏。
- 升级前打过的老牌局同样能回放（盲注座位由服务端推出）。若某手提示「记录不完整，无法回放」，查服务端日志 `hand replay could not be rebuilt` 并把手号告诉开发者。

**I-6. AI 复盘（服务端必测，需要配置 `REVIEW_API_KEY`、一个管理员账号和至少两个普通账号）**
管理员打开「服务器管理 → AI 复盘管理」。预期：顶部显示「大模型：<型号>」；没配置密钥时显示「服务端没有配置大模型」。给账号 A 开通、B 不开通，两人打几手（包括打到摊牌的一手）。
- A 在回放页看到「AI 复盘」按钮，B 看不到。A 点下去后右侧抽屉显示「正在分析」，通常半分钟到两分钟后自动出结果：总评、逐步点评、要点、对手倾向、结果回顾。点一条逐步点评会跳到那一步，信息栏显示「AI：<结论>」。
- 逐步点评里的每一步都是 A 自己的行动；点评里只出现位置（BTN、BB 等），不出现任何人的昵称；没摊牌的对手的牌不出现在任何地方。
- 关掉回放再打开同一手，按钮变成「查看 AI 复盘」，不会重新分析；审计记录里有开通操作；管理页的用量随之增加。
- 管理员把「每人 24 小时内次数」设为 1：A 再对另一手发起时提示「24 小时内的复盘次数已用完」。关掉总开关后 A 的按钮消失。
- 把 `REVIEW_MODEL` 改成一个不存在的型号重启：发起后显示「大模型服务暂时不可用」，可以重新分析；服务端日志有 `hand review failed`，客户端看不到模型服务的报错原文。

**I-4. 抽水（服务端必测，必须接 PostgreSQL；需要一个管理员账号和至少两个普通账号）**
管理员在「抽水管理」给房间设 5%、封顶 50、翻后加抽 10（盲注 10/20）。预期：
- 房间里每个人的文字聊天都出现一条「系统公告」，写明 5%、最多 50、加抽 10、下一手起生效；聊天收起时有提示和未读角标；屏蔽了任何玩家都不影响它显示。
- **正在打的这一手不抽**，下一手才开始。
- 翻牌前全员弃牌给大盲的一手：只对盲注部分按比例抽，没有加抽；加注者被退回的筹码不计入。
- 打到翻牌之后的一手：结算区写「本手抽水 X」，X = 向下取整(底池×5%)（不超过 50）+ 10；各人分到的数额之和 + X = 底池。
- 发两次的一手只抽一次。
- 短码全下产生边池的一手：主池赢家照常分到主池（只少了主池自己那份抽水），不会出现牌最大却没有分到筹码。
- 牌桌信息栏常驻显示「抽水 5%，最多 50；翻后加抽 10」；另一个账号输入房间码后，带入窗口里写着「本房间抽水：…」。关闭抽水后这两处都消失。
- 管理员钱包增加的数额与「抽水管理」页该房间的累计、合计一致；管理员「筹码流水」里每手一条「牌桌抽水」。对账：
`SELECT reference_id, wallet_delta FROM bankroll_entries WHERE reason = 'rake' AND room_id = '<房间ID>' ORDER BY created_at;`
- 关闭抽水后聊天里再出现一条公告，下一手起不抽。房间关闭后「抽水管理」页仍能看到它的累计并标注已关闭。
- 管理员账号在大厅创建或加入房间被拒，并说明原因；房主在任何地方都找不到修改抽水的入口。
- 每手跑对账脚本无差异（`/opt/texas/bin/texas-reconcile.sh`）。

**J. 进程被系统回收后回到应用（Android / HarmonyOS 必测）**
牌局进行中把 App 切后台，等到被系统回收（或用开发者选项「不保留活动」/`adb shell am kill` 强制），再重新打开。预期：**不出现登录页，直接落回原来那一桌**，手牌、底池、公共牌与其他玩家看到的一致。这条依赖设备上存着的刷新令牌，Web 端刻意不持久化，因此不适用。

**K. 断网启动与恢复联网（Android / HarmonyOS 必测）**
先正常登录一次（令牌落盘），杀掉应用，开飞行模式后启动。预期：**短暂等待后显示登录页，而不是长时间转圈**（恢复有 8 秒总超时）；此时关掉飞行模式，把应用切后台再切回前台，预期**自动登回去**，不必手动输密码。这条是自动化测试无法覆盖的：生命周期回调在本项目的 Flutter OpenHarmony 分支上无法在测试里驱动。

**L. 弱网下启动不丢登录态**
`Slow 3G` 下重复启动应用若干次。预期：**不会出现「用过一次就要重新登录」**。只有服务端明确拒绝令牌时才清除，没网、超时、服务端 5xx 一律保留。

**M. 服务端重启后牌局继续（服务端必测）**
牌局进行到翻牌圈时重启游戏服务容器（`docker restart`，不给排空时间以模拟崩溃）。预期：玩家重连后**这一手照原样继续**，手号、底池、行动位不变，行动倒计时从重连时刻重新起算；打完后筹码守恒。若客户端提示「本手作废」，说明恢复被放弃，需要查服务日志里的放弃原因。**该功能要求服务端接入 PostgreSQL**；未接数据库的部署仍是作废。

### 2.4 事后核对

弱网验收结束后跑一次对账，确认筹码守恒没有被异常路径破坏：

```bash
/opt/texas/bin/texas-reconcile.sh
```

## 3. 发布冒烟清单

四端各跑一遍。历史上这些问题**只在真机暴露**，自动化测试全绿也必须逐条走。

### 3.1 通用（每端都要）

- [ ] 版本号正确：关于页/包信息显示的版本与本次发布一致（用 `dart tool/set_version.dart <版本号>` 一次改完三处），HarmonyOS 的 `versionCode` 已同步。
- [ ] 注册页与个人信息页能打开《隐私说明》。
- [ ] 注册 → 登录 → 建房 → 加入 → 打完一手 → 离桌 → 退出登录，全程无异常。
- [ ] 钱包流水中文显示正确，无英文原始码（例如不应出现 `account_deletion`）。
- [ ] 管理员能进「服务器管理」和「审计记录」；**普通玩家看不到入口**。

### 3.1.1 观战位（OB）

- [ ] 手间点「进入观战」能让出座位；观战面板的「上桌」能坐回去。
- [ ] 牌局进行中申请上桌只记意向，本手结算后入座；座位满时当场拒绝。
- [ ] 付费观战者能看到所有参与者的手牌；**普通玩家看别人的座位仍只有牌背**。
- [ ] 筹码不足时提示补码而不是静默看不到牌；补码后下一手恢复。
- [ ] 房主关闭观战者的语音后，正在开麦的观战者被自动关麦。
- [ ] 房主能在「房间管理」里看到并移出观战者。
- [ ] 右上角人数显示为 `X/N（OB: Y）`，点开是房间名单。

### 3.2 牌桌布局（历史重灾区）

- [ ] **2 人、6 人、10 人**三种桌型座位排布正确，无重叠、无溢出。
- [ ] 图层顺序：公共牌背景 < 玩家框 < 本轮下注筹码 < 赞赏/嘲讽气泡。
- [ ] 本人手牌和摊牌在**玩家框内**；两块公共牌不遮挡任何玩家的摊牌。
- [ ] 发两次：两块牌面先后展示完整，自动准备倒计时为 **15 秒**。
- [ ] 窄窗口 Windows 与手机横屏下动作栏、聊天、语音控件都可达。

### 3.3 键盘与安全区（Android / HarmonyOS 必测）

- [ ] 登录页、大厅页弹出软键盘：**布局不抽搐、输入框不失焦、键盘不自动收回**（平板尤其要测）。
- [ ] 金额与房间码输入：HarmonyOS 使用自定义横屏数字面板。
- [ ] 挖孔屏安全区正确避让，牌桌内容不被摄像头挖孔遮挡。

### 3.4 语音

- [ ] 加入语音后双向可听；**HarmonyOS 重点验证开麦后能否持续听到其他人**（历史上音频路由会被抢占）。
- [ ] 单独静音某人、屏蔽某人分别生效；**取消屏蔽后仍处于静音的人不应恢复出声**。
- [ ] 退出语音不断开牌局。

### 3.5 交互

- [ ] 换位：两手之间点击其他玩家发起申请，对方确认后生效；**未坐满时也能发起**。
- [ ] 私下看牌：已弃牌玩家申请查看，对方同意后仅申请者可见，标签显示「私下查看」。**同意过一次后再点同一玩家，提示「你本手已经看过 X 的牌」而不再发申请。**
- [ ] 拒绝范围：被申请者的弹窗底部只有「拒绝 / 同意」，范围选项以整行按钮放在正文里（换位一项「不再接受此人的换座申请」，看牌两项「本手不再接受此人 / 任何人的看牌申请」）。鸿蒙手机横屏并开系统大字号时，正文能滚动到可读、范围按钮能点到，「拒绝」「同意」始终同一行。选「不再接受此人」后申请者再申请，**立刻**收到「X 不再接受你的换座申请」，被申请者不再弹窗；申请者退出房间再进来仍然被拒；被申请者退出再进来后才能再申请。看牌的屏蔽在本手结束后失效。
- [ ] 申请偏好：设置弹窗里「换座与看牌申请」两个开关（观战者看不到这一项）。关掉「允许换座」后别人申请，申请者立刻看到「X 不接受换座申请」；关掉时若已有排队申请，弹窗不再出现。退出房间再进来两个开关恢复为开。
- [ ] 拒绝提示只有申请者看到：第三名玩家的界面上没有任何「谁拒绝了谁」的提示。
- [ ] 中途加入显示为「待入座」，本手结算后入座。
- [ ] 补码：筹码归零时自动弹出，金额上限正确。
- [ ] 注销账号：房间内应拒绝并提示；房间外注销后原用户名可重新注册。

### 3.6 打包与签名

- [ ] Android Release 使用正式签名（`android/key.properties` 已配置），**能覆盖安装上一版本**。
- [ ] HarmonyOS Release 签名可用，能安装到真机。
- [ ] Web 构建在目标浏览器可用，WebSocket 与 TRTC 均连通。
- [ ] 安装包不包含任何 `.env`、密钥或证书。
