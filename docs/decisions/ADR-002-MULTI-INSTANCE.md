# ADR-002：多实例与 Redis

> 状态：已接受——**暂不实施**。触发条件、设计约束与验收标准已在本文明确，实施前不需要重新讨论要不要做，只需确认触发条件是否成立。
>
> 日期：2026-09-02

## 背景

当前生产环境是一台腾讯云轻量应用服务器，跑一个 `texas-game-server` 容器和一个 PostgreSQL 容器。运行中的牌桌是**单实例内存单写者**：牌局引擎、行动截止时间、定时器都在进程内存里，PostgreSQL 只保存已结算的手和结算后的筹码。

交接文档长期把「多实例」列为 P2，并要求上线前必须证明同一牌桌不会双写且筹码守恒。本文回答三个问题：多实例能解决什么、当前架构差在哪里、什么条件下才值得做。

## 多实例能解决什么，不能解决什么

先分清三种诉求，它们的答案不一样。

| 诉求 | 多实例是否解决 | 说明 |
|---|---|---|
| **容量** | 能，但不需要 | 熟人私人牌局，峰值是十几个人、两三桌。单实例离瓶颈还很远，且尚无任何证据表明存在容量问题 |
| **崩溃可用性** | 部分解决 | 进程崩溃时其他实例可以接管**新的**牌局；但崩溃实例上**正在进行的那一手无法恢复**（见下文），玩家照样要重来 |
| **无中断部署** | **不解决** | 牌桌绑定在某个实例上，更新那个实例仍会打断它上面的牌局。要做到不中断，需要的是「牌桌迁移」或「优雅停机等待手间空档」，而不是多开一个进程 |

结论：多实例的收益主要落在崩溃可用性上，而且只是部分。**它并不能解决真正让人难受的那个问题（部署要停牌局），那个问题有成本低得多的解法。**

## 当前阻碍多实例的进程内状态

这份清单是「简单启动第二个容器」会立刻出错的完整原因。

| 状态 | 位置 | 多实例下会发生什么 |
|---|---|---|
| 牌桌运行时（引擎、截止时间、亮牌与换位申请、加时卡、`pendingCashOuts`） | `Manager.tables` 进程内存 | 两个实例各持一份，同一桌双写，**筹码不守恒** |
| 行动与自动准备定时器（`time.AfterFunc`） | 进程内存 | 持有实例崩溃后无人推进超时，牌局永久卡住 |
| WebSocket 客户端表（`hub.clients`） | 进程内存 | 同桌玩家连到不同实例时互相收不到快照 |
| 事件缓冲（`EventBuffer`，序号补发） | 进程内存 | 重连到另一实例，序号不连续且无法补发 |
| 幂等缓存（`RequestCache`，每用户 256 条） | 进程内存 | 重连到另一实例后，重复 `requestId` 会被**再执行一次** |
| 用户串行锁（`userLocks`） | 进程内存 | 跨实例不互斥，同一用户的两条命令可并发进入引擎 |
| 语音成员状态（`hub.voice`） | 进程内存 | 只广播到本实例的连接，语音名单不全 |
| 在线状态（`presenceTracker`） | 进程内存 | 管理台看到的在线情况只反映本实例 |
| 限流令牌桶（`internal/ratelimit`） | 进程内存 | N 个实例等于 N 倍配额，限流形同虚设 |
| 聊天历史与聊天限流 | 进程内存（历史另有 PostgreSQL 副本） | 历史可回源，限流同上 |

其中前两项是**正确性**问题，其余是功能退化。正确性问题不能靠「多试几次」解决。

### 一个容易被低估的约束：快照按接收者裁剪

`broadcastSnapshots` 对**每个接收者单独生成**快照——底牌只出现在本人的那一份里。这意味着跨实例广播不能是「把一份快照发到频道上」，而必须按 `userID` 定向投递。这既增加复杂度，也把「底牌泄漏给错误的人」从一个不可能事件变成一个需要靠代码正确性保证的事件。对一个以隐藏信息为核心的牌类游戏，这个风险的性质和「消息晚到几百毫秒」完全不同。

## 决策

**暂不实施多实例，继续以单实例内存单写者运行。** 同时：

1. 不再在文档中把多实例描述为「待办」，而是描述为「已评估、暂缓、有触发条件」。
2. 不做任何「为将来多实例做准备」的预埋改造。没有明确触发条件的抽象层只会增加当前代码的复杂度。
3. 把资源投向下文「先做的替代方案」，它们用小得多的代价解决真实痛点。

## 若要实施：设计约束

以下是重新评估后决定实施时**必须**满足的约束。不满足其中任何一条都不允许上线多实例。

### 1. Redis 里放什么

只放**租约与路由**，不放牌桌权威状态：

| 键 | 内容 | TTL |
|---|---|---|
| `table:{roomID}:lease` | 持有该牌桌的 instanceID + 单调递增的 epoch | 10 秒，持有者每 3 秒续约 |

**不把牌桌运行时状态放进 Redis。** 理由：Redis 的持久化（即使 AOF `everysec`）仍可能丢最后一秒的写入，把权威状态放进去等于把单点从进程搬到 Redis，同时还引入了序列化开销和不一致窗口。权威事实仍然是：已结算的手在 PostgreSQL，进行中的手在租约持有者的内存里。

### 2. 单写者租约

- 只有持有租约的实例可以修改牌桌、运行定时器、写结算。
- 获取用 `SET key value PX 10000 NX`，续约用 Lua 脚本比对持有者后再延期，避免误续他人的租约。
- **续约失败时，持有者必须立即停止推进该牌桌并丢弃其定时器**，不能等到 TTL 自然过期。这是防双写的关键动作。
- 租约 TTL 必须大于最坏情况的 GC 暂停加网络抖动。仅靠 TTL 不足以防双写：进程可能在续约失败后、自我停止前被调度器挂起。因此必须叠加下一条。
- **Fencing**：租约 epoch 随每次易主递增；结算写入 PostgreSQL 时带上 epoch，数据库侧校验「本桌已记录的最大 epoch」，拒绝来自旧持有者的写入。没有 fencing 的租约不是互斥。

### 3. 实例崩溃后的状态恢复

必须正视一件事：**进行中的那一手无法恢复。** 已发的底牌、洗牌用的随机状态都只在崩溃进程的内存里，没有任何地方可以重建它们，也不应该为此把底牌写进外部存储。

因此接管协议只能是：

- 新持有者从 `room_members` 重建牌桌（座位与筹码是**上一手结算后**的值），当前手直接作废。
- 由于本手的投入从未写入数据库，作废等于什么都不用退——但**客户端必须明确显示「本手作废」**，不能让玩家以为自己的下注凭空消失。这需要新增一个协议消息或快照字段。
- 熟人局可以接受偶尔重来一手；这个前提如果不成立，多实例方案本身就不成立。

### 4. 客户端路由

推荐**按房间码一致性哈希，同桌同实例**（方案 A），代价是需要协议改动：当前客户端先 `session.authenticate` 再 `table.join`，房间号在消息体里，反向代理在建连时看不到，必须改为在连接 URL 上携带房间码。

不推荐「任意实例接入 + 跨实例转发」（方案 B）：它要求按 `userID` 定向投递裁剪后的快照，复杂度和底牌泄漏风险都显著更高。

### 5. Redis 故障降级

这是最需要诚实面对的一条：**引入 Redis 会把「一个单点」变成「两个单点」。** Redis 不可用时所有实例都无法续约，按第 2 条它们都必须停止推进牌桌，结果是全站不可用——比现在更差。

允许的缓解只有一种：配置开关式的单实例回退模式，且**必须人工确认后才能启用**。自动降级会在网络分区时直接制造脑裂和双写。

## 验收标准

上线前必须**证明**以下几点，只有测试通过的记录才算数：

1. **混沌测试**：牌局进行中 `kill -9` 租约持有者，另一实例接管；牌局能继续进行，`texas-reconcile.sh` 对账 0 差异。
2. **双写拦截**：人为制造两个实例同时自认为持有租约（跳过续约校验），fencing 必须让旧持有者的结算写入**失败**，而不是产生两份结算。
3. **现有属性测试跨实例复跑**：`manager_churn_property_test.go` 的成员进出与筹码守恒不变式在双实例拓扑下同样成立。
4. **隐藏信息**：跨实例场景下的自动化断言，证明任何玩家都不会收到他人的底牌。
5. **24 小时观测**：按[验收指南](../ACCEPTANCE_GUIDE.md)在双实例拓扑上跑通，两个实例都通过判定。

## 先做的替代方案

这些用小得多的代价解决真实痛点，应当优先于多实例：

1. **优雅停机等待手间空档**（直接解决部署中断）。**已于 2026-09-02 实现**，见协议文档 6.8：此前 `SIGTERM` 后只调用 `server.Shutdown`，10 秒后进程退出，正在进行的手直接丢失；现在收到信号后停开新局、取消自动准备并广播原因，等所有牌桌到达手间空档（上限 `SHUTDOWN_DRAIN_TIMEOUT_SECONDS`，默认 120 秒）再退出。配合客户端已有的 1-2-4-8 秒重连退避，一次更新对玩家的可感中断压到几秒。
2. **重启后明确告知客户端本手作废**。**已于 2026-09-02 实现**：`session.authenticated` 携带 `serverInstanceId`，客户端在重连后发现标识变化且上一份快照仍在手中，即提示「本手作废、筹码已恢复到上一手结算后」。这也是多实例接管需要的同一能力（见设计约束第 3 条）。
3. **容量测量**。在真正需要讨论扩展之前，先用 24 小时观测拿到真实的连接数、内存与 CPU 曲线。没有测量就谈扩容是没有依据的。

## 重新评估的触发条件

出现以下任一情况时重新打开本决策：

- 观测显示单实例在真实负载下 CPU 或内存持续接近上限。
- 牌局中断（崩溃导致）在一个月内发生超过一次，且优雅停机与快速重启已无法进一步改善。
- 产品定位改变，不再是熟人私人牌局（此时隐藏信息与「重来一手」的前提都要重新评估）。

## 代价与风险（不实施的那一面）

- 进程崩溃时，该实例上所有进行中的手都会作废。缓解手段是健康巡检告警（已上线）与快速重启，不是消除。
- 更新服务仍需要几秒中断（进程重启与客户端重连），但不再打断进行中的手；排空超时（默认 120 秒）仍未结束的手会作废。
- 服务器本身是单点。整机故障的恢复依赖备份与恢复演练（见[备份与恢复指南](../BACKUP_AND_RESTORE_GUIDE.md)），恢复目标是数据不丢，而不是牌局不断。
