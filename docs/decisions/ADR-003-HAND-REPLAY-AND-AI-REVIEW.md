# ADR-003：牌局回放与大模型复盘（1.0.0）

> 状态：**已接受，分两步实施**。回放在 0.8.0 完成（第 1、2 阶段）；AI 复盘在回放稳定后另行开发（第 3、4 阶段）。第 7 节的问题已于 2026-09-23 拍板，结论见第 8 节。
>
> 日期：2026-09-23

## 1. 需求理解

1.0.0 要加的是两件相关但性质不同的事：

| | 牌局回放（录像） | 大模型复盘 |
|---|---|---|
| 是什么 | 在「牌局记录」里像看录像一样重放自己打过的某一手，**每名玩家的每一次行动是一个时间步**，可播放、暂停、逐步前进/后退 | 把这一手里**当前用户**的决策连同必要的局面信息发给大模型，由它给出详细复盘，结果回到用户界面展示 |
| 数据来源 | 服务端已保存的牌谱 | 同上，外加服务端预先算好的数值事实 |
| 外部依赖 | 无 | 大模型服务（要花钱、要出网、要把数据交给第三方） |
| 主要风险 | 隐藏信息泄露（别人没亮的底牌） | 隐私、费用、可用地区、分析质量 |

需求中「只对管理员开放，后续再考虑普通用户」这一条，与 0.7.0 的规则直接冲突，见第 5 节。

## 2. 现状梳理：和这个功能相关的部分

### 2.1 服务端已经保存了什么

每手结算后，`tablemanager.persistSettlementLocked` 组装一条 `history.Hand` 写入 PostgreSQL（迁移 000001 的 `hands`、`hand_players`、`hand_actions` 三张表，000012 加了 `hands.rake`）：

| 字段 | 内容 | 对回放够不够 |
|---|---|---|
| `hands.dealer_seat` | 庄位座号 | 够 |
| `hands.board_cards` | 最终公共牌（最多 5 张，按发出顺序：前 3 张翻牌、第 4 张转牌、第 5 张河牌） | 够，街次可由张数推出 |
| `hands.runout_boards`、`pot_awards`、`revealed_hands`、`showdown`、`rake` | 发两次的两块牌面、各池分配（已扣抽水）、亮牌、是否摊牌、抽水 | 够 |
| `hand_players` | 每名参与者的座号、昵称、**起始/结束筹码**、输赢、**两张底牌（所有人的都存了）** | 够 |
| `hand_actions` | 每个动作：顺序号、街、类型（fold/check/call/bet/raise/all_in）、**本次投入**（`committed`，是增量不是累计）、`raise_to`、时间 | 基本够，缺口见下 |

结论：**不需要改变牌局本身，已有数据就能重放绝大多数牌谱，包括上线前打过的历史手牌。**

### 2.2 缺口

| 缺口 | 影响 | 处理 |
|---|---|---|
| **盲注不是动作**：`StartHand` 直接 `postBlind`，没写进 `hand_actions` | 回放第一帧不知道谁下了多少盲注 | 旧牌谱可推导：盲注额取自房间（`rooms` 的盲注建房后不可改），盲注位按引擎规则由庄位推出（两人时庄位是小盲），短码盲注全下时投入取 `min(盲注, 起始筹码)`。新牌谱在 `hands` 上直接记下大小盲座位与金额，免得推导逻辑和引擎将来分叉（需新迁移） |
| 未被跟注的退回没单独存 | 最后一帧显示的底池会比实际争夺的大 | 由动作序列算出（与引擎的 `BuildPots` 同一口径），并用「起始 − 总投入 + 分得 + 退回 = 结束」对每名玩家自检 |
| 发两次的协商过程、加时卡、私下看牌、结算后亮牌的时刻 | 不影响筹码与决策 | 回放不展示；发两次只在最后标注「双方同意发两次」 |
| 超时自动过牌/弃牌 | 已记录为普通动作，但看不出是超时 | 可选：新牌谱加一个 `timed_out` 标记；复盘时「超时弃牌」和「主动弃牌」意义不同 |
| 历史只能查最近 20 手（`GET /v1/hands/recent?limit=`，上限 100），没有按手号取单手的接口 | 牌局记录翻不到更早的手 | 新增分页列表与单手接口（见 4.2） |

### 2.3 可见性契约——最要紧的一条

`history.Store` 的注释写得很清楚：库里存的是**所有人**的底牌；发给客户端之前必须用 `forRecipient` 裁剪，只保留请求者自己的底牌和那一手真正亮出来过的底牌。回放和复盘都必须沿用这条契约：

- 回放时间轴**在服务端生成并裁剪**，客户端拿不到任何没亮过的对手底牌。不能把完整牌谱发给客户端、靠界面隐藏。
- 发给大模型的内容同样按「请求者当时能看到什么」裁剪，并且要区分「决策当时已知」与「事后亮牌才知道」的信息（见 4.4）。

### 2.4 客户端能复用什么

- `TableCanvas`（座位、下注筹码、庄位、公共牌区、摊牌显示）是纯展示组件：输入是 `List<TableSeat>` 加一个 `TableSnapshot`，**不依赖 WebSocket 连接**。回放可以为每一帧构造一份快照喂给它，牌桌外观、手机横屏布局、图层顺序与现有牌桌完全一致，不必另画一套。
- `TableBoardCenter` 已支持发两次、多池分配、抽水说明。
- 入口放在已有的「最近牌局」（`RecentHandsPage`），它已经按街展示动作文字。
- 管理后台已有「服务器管理」页、审计页、抽水页的写法可以照搬（开关、名单、用量统计）。

### 2.5 服务端能复用什么

- HTTP 路由风格、`authenticateRequest` / `AuthorizeAdmin`、审计写入、错误码映射都现成。
- 牌型评估器（`holdem` 包）可以直接用来给复盘算「此刻的牌型」「对随机手牌的胜率」等数值事实。
- 配置从 `.env` 读，敏感值（如 TRTC SecretKey）已有处理先例，大模型 API 密钥照同样规矩处理。
- 服务端目前**没有任何对外发起的业务 HTTP 调用**（TRTC 签名是本地计算的）。复盘会是第一个，需要处理超时、重试、出网与费用。

## 3. 评估结论

| 部分 | 可行性 | 难点 | 规模估计 |
|---|---|---|---|
| 回放 | 高。数据齐全，渲染可复用 | 盲注推导、退回计算、服务端裁剪、手机横屏上的播放控件 | 中：服务端一个时间轴生成器 + 两个接口；客户端一个播放页 |
| 大模型复盘 | 技术上可行 | **不在代码里的问题更大**：供应商能否在你的服务器所在地访问、隐私说明要改、费用要设上限、分析质量需要评估 | 中偏大：异步任务、缓存、限额、结构化输出、结果页 |

建议把两件事拆开交付：**回放没有外部依赖和隐私成本，可以先做完、甚至直接对所有人开放；复盘在回放之上叠加，按名单灰度。** 复盘结果里每条点评都挂在某个时间步上，点一下就跳到回放的那一步——这是两者合在一起才有的体验，也是先做回放的理由。

## 4. 设计

### 4.1 回放时间轴（服务端生成）

新增 `internal/replay` 包，输入一条完整的 `history.Hand` 和房间盲注，输出按请求者裁剪后的时间轴：

```
Timeline {
  handId, roomCode, startedAt, smallBlind, bigBlind, dealerSeat, rake
  players: [{seat, displayName, startingStack, position("BTN"/"SB"/"BB"/"UTG"…), isViewer, holeCards(仅本人或亮过的)}]
  steps: [
    { index, kind: "deal" | "blind" | "action" | "street" | "refund" | "showdown" | "award",
      actorSeat, action, committed, raiseTo, street, board(截至此步已发出的公共牌),
      pot, stacks{seat: 剩余}, streetBets{seat: 本街已投}, toCall, folded[] , note }
  ]
  result: { potAwards, runoutBoards, revealedHands(裁剪后), deltas }
}
```

- 每个玩家动作是一步；街切换（发翻牌/转牌/河牌）、全下后补发公共牌、未被跟注的退回、摊牌、分池各是一步，这样「录像」才连贯。
- 每一步都带完整状态（筹码、底池、本街投入），客户端不需要自己累加，前进后退只是换一帧。
- **自检**：生成完用「起始 − 总投入 + 分得 + 退回 = 结束筹码」核对每名玩家，再核对「各人输赢之和 + 抽水 = 0」。对不上就返回 `replay_unavailable` 并写日志，绝不显示一份算错的录像。老牌谱若有推导不了的边角（例如某些早期版本的数据），同样安全退化。
- 为什么放服务端：裁剪必须在服务端；盲注位、退回等规则只在 Go 里有一份；四个平台共用一份结果。

另一种做法是用规则引擎本身重跑这一手（注入已知牌序和庄位，逐个提交记录的动作），状态绝对一致，但要给引擎加「指定牌序」「指定庄位」「指定抽水额」等只为回放存在的入口，并且要处理引擎规则日后变动导致老牌谱重放不出来的问题。**建议采用独立推导 + 自检，不动引擎。**

### 4.2 接口

全部是 HTTP（回放和复盘都不需要实时推送），需登录：

| 方法与路径 | 作用 | 权限 |
|---|---|---|
| `GET /v1/hands?before=<handId>&limit=` | 牌局记录分页（替代只能取最近 N 手的现状） | 本人 |
| `GET /v1/hands/{handId}/replay` | 回放时间轴 | 必须是该手参与者，否则 404（不泄露手号是否存在） |
| `POST /v1/hands/{handId}/review` | 发起复盘；已有结果直接返回，不重复花钱 | 本人 + 复盘权限 |
| `GET /v1/hands/{handId}/review` | 查询复盘状态与结果 | 本人 + 复盘权限 |
| `GET/POST /v1/admin/review/...` | 开通名单、全局开关、用量与费用统计 | 管理员 |

### 4.3 复盘任务

大模型一次分析通常要十几秒到一分钟，不能挂在一个 HTTP 请求上等：

- 新表 `hand_reviews`（新迁移）：`hand_id, user_id, status(queued/running/done/failed), prompt_version, model, result jsonb, input_tokens, output_tokens, error, created_at, finished_at`，`(hand_id, user_id, prompt_version)` 唯一——同一手、同一人、同一版提示词只分析一次，结果永久缓存。
- 进程内一个后台工作协程顺序处理队列；服务重启时把 `running` 的任务重新入队。单实例部署，这样足够（与 ADR-002 一致，不引入队列中间件）。
- 客户端发起后轮询 `GET .../review`，界面显示「分析中」。
- **额度**：每人每日次数上限、全服每月 token 或费用上限，超出返回明确的错误码，由管理员在后台调整。每次调用记录 token 用量，后台可看。
- 失败（超时、限流、供应商拒绝）记为 `failed`，允许用户重试。（实现时修订：**失败的那次不占每人次数**，只数排队、进行中和已完成的；否则上限设成 1 时赶上一次模型出错，玩家什么都没拿到却再也不能重试。失败消耗的 token 照样计入全服预算，预算兜住反复失败的费用。）

### 4.4 发给大模型的内容

原则：**事实由服务端算，模型只负责解释与判断。** 大模型心算底池、赔率很容易算错，不能让它自己算。

对当前用户的每一个决策点，服务端给出：

- 位置、剩余人数、有效筹码、筹码深度（以大盲计）、SPR；
- 底池、需跟注额、底池赔率、最小加注额；
- 本人此刻的牌型与听牌情况，以及对随机手牌的胜率（用现有评估器做蒙特卡洛）；
- 此前每名对手在本手的动作序列；
- 本人实际的选择与金额。

整手信息：盲注、各人起始筹码（以位置称呼）、公共牌、结果。

**隐私处理：**

- 不发送用户 ID、昵称、房间码。对手一律用位置称呼（「BTN 玩家」「BB 玩家」）。
- 对手没亮过的底牌永远不发。
- 摊牌亮出的底牌单独标为「事后信息」，并在提示词里要求模型：**评价每个决策只能用决策当时可知的信息**，事后信息只用于「结果回顾」一节。否则复盘会变成「你该知道他有同花」式的马后炮。

**输出格式**：用结构化输出（JSON Schema）约束，客户端原生渲染，不引入 Markdown 渲染库：

```
{ summary: 一段总评,
  decisions: [{ step: 对应回放的时间步, verdict: "好"|"合理"|"有争议"|"失误", reasoning, betterOption? }],
  keyLessons: [..], hindsight: 结合亮牌的结果回顾 }
```

`decisions[].step` 就是回放时间轴的 `index`，客户端据此把点评贴到录像上。

### 4.5 大模型接入

- 服务端定义一个 `Reviewer` 接口（输入上面的结构化事实，输出上面的结构化结果），供应商实现放在它后面，通过配置选择。这样供应商能换、测试能用假实现，也能在没配密钥时整体关闭功能。
- 若使用 Anthropic 的 Claude：用官方 Go SDK（`github.com/anthropics/anthropic-sdk-go`），模型默认 `claude-opus-5`（可配置），开启自适应思考，用 `output_config.format` 做结构化输出，把固定的系统提示词设为缓存以降低每次的输入费用。
- 费用量级（按 Claude Opus 5 的公开价，输入 $5 / 输出 $25 每百万 token）：一手牌的输入约 3～6 千 token，输出连同思考约 3～8 千 token，**每次约 0.1～0.25 美元**。十几个熟人偶尔用，每月是个位数到几十美元；开放给所有人、每手都点，费用会随手数线性上涨，所以额度必须在第一版就有。
- 密钥（如 `ANTHROPIC_API_KEY`）与 TRTC SecretKey 同级处理：只放服务器 `.env`，不进仓库、不进日志、不下发客户端。**客户端永远不直接调用大模型。**
- 配置项草案：`REVIEW_ENABLED`、`REVIEW_PROVIDER`、`REVIEW_MODEL`、`REVIEW_DAILY_LIMIT_PER_USER`、`REVIEW_MONTHLY_TOKEN_BUDGET`、`REVIEW_TIMEOUT_SECONDS`。

### 4.6 客户端

- 「最近牌局」改为可翻页的「牌局记录」，每手多一个「回放」按钮；有复盘权限的人再多一个「AI 复盘」。
- 回放页：复用 `TableCanvas` 与 `TableBoardCenter` 渲染每一帧；底部控件为播放/暂停、上一步/下一步、进度条（按街打标记）、倍速。手机横屏高度紧，控件要与牌桌共用一条窄栏，需真机检查（按项目约定覆盖窄 Windows、手机、2/6/10 人、发两次）。
- 复盘结果：总评、逐条决策点评（点击跳到对应步）、要点、事后回顾。状态：未开始 / 分析中 / 完成 / 失败（可重试）/ 额度用完。
- 所有新错误码映射为中文。首次使用复盘时弹出一次说明：内容会发送给哪家大模型服务、发送了什么、不发送什么，确认后才发起。

## 5. 必须先处理的冲突与风险

### 5.1 「只对管理员开放」与 0.7.0 的规则冲突

0.7.0 起**管理员账号不能创建或加入牌桌**（`admin_cannot_play`）。所以管理员账号在 0.7.0 之后没有自己的新牌局，「管理员复盘自己打过的牌」基本无牌可复盘。可选方案：

| 方案 | 做法 | 代价 |
|---|---|---|
| **A. 名单开通（推荐）** | 管理员在后台给指定账号开通「AI 复盘」（例如管理员自己另注册的普通号和几位愿意试用的朋友）；被开通的人复盘**自己的**牌局。之后全面开放就是把默认值改成「开通」 | 多一个用户级开关与后台名单页 |
| B. 管理员查看任意玩家视角 | 管理员选择某位玩家的某一手，以他的视角回放并复盘 | 管理员能看到玩家**从未亮过的底牌**。这是新的越权能力，与现有「底牌只对本人可见」的承诺冲突，隐私说明要大改，每次查看都要审计 |
| C. 放开管理员上桌 | 撤销 0.7.0 的限制 | 抽水收款人坐在桌上，0.7.0 刻意避免的问题重新出现 |

### 5.2 隐私说明必须改

`docs/PRIVACY_NOTICE.md` 现在写着数据「不会提供给任何第三方」。复盘会把牌局数据发给大模型服务商，上线前必须：

- 改写隐私说明，写清发送哪些内容、不发送哪些内容（昵称、ID、未亮底牌都不发）、发给谁；
- 每个用户第一次使用时明确同意；
- 在 `CLAUDE.md` 与交接文档的产品边界里加一条，说明这是唯一向第三方发送数据的功能。

### 5.3 供应商的可用地区（可能决定能不能做）

Anthropic 的 API 只在其支持的国家和地区提供服务，**中国大陆不在其中**。生产环境是腾讯云轻量服务器：

- 如果服务器在中国大陆，服务端直接调用 Claude API 不可行，也不应通过代理绕过供应商的地区限制；
- 如果服务器在支持的地区（例如中国香港以外的海外地域，需以 Anthropic 当时公布的支持列表为准），可以直接调用。

这就是 4.5 要求「供应商可替换」的原因：若服务器所在地无法使用 Claude，就接入该地区合规可用的其他大模型服务，接口与客户端不受影响。另外，面向公众提供的生成式 AI 服务在中国大陆有专门的管理规定；本项目是熟人私用、名单开通，但如果将来要对所有人开放，建议先确认适用性（这不构成法律意见）。

### 5.4 分析质量

- 大模型不是扑克求解器，给出的是「有道理的点评」，不是精确最优策略。界面上要标明「仅供参考」。
- 上线前先挑 20～30 手有代表性的牌（弃牌、偷盲、全下、发两次、边池、超时），人工看一遍结果，再决定提示词和模型，并把这组牌留作以后调整提示词时的回归检查。
- 熟人局最有价值的其实是「针对这几位朋友的打法倾向」。从历史牌谱统计对手的入池率、加注率等，可以在第二阶段作为额外事实提供给模型（统计的是本人见过的公开动作，不涉及未亮底牌）。

### 5.5 其他

- 回放里对手的昵称是牌谱记录时的昵称，账号注销后仍会显示原昵称；这与现在「最近牌局」一致，隐私说明已覆盖。
- 复盘结果缓存后，提示词或模型升级会使旧结果与新结果口径不同；用 `prompt_version` 区分，允许用户「用新版重新分析」（计额度）。

## 6. 分阶段计划

| 阶段 | 内容 | 可单独上线 |
|---|---|---|

## 7. 需要拍板的问题

1. **权限模型**：采用名单开通（方案 A），还是管理员查看任意玩家视角（方案 B）？
2. **回放是否对所有人开放**？它没有外部依赖和额外隐私成本。建议开放，只把 AI 复盘放进名单。
3. **生产服务器在哪个地域**？这决定能不能用 Claude，还是要选其他大模型服务。
4. **复盘能否使用摊牌亮出的对手底牌**？建议只放在单独的「结果回顾」一节，决策点评只用当时可知的信息。
5. **费用上限**：每人每日几次、全服每月多少预算？
6. **复盘的语气与详细程度**：面向新手的讲解式，还是面向熟练玩家的简练式？

## 8. 拍板结论（2026-09-23）

1. **权限：名单开通。** 管理员在后台给指定账号开通 AI 复盘，被开通的人复盘自己的牌局。
2. **回放对所有玩家开放。** 每名玩家在回放中只能看到自己的底牌，以及最后摊牌亮出的牌（如有）。结算后自愿亮牌、私下看牌不进入回放。已在 0.8.0 实现。
3. **大模型初步选用 DeepSeek 或通义千问**，不再考虑地域问题。第 4.5 节「供应商可替换的 `Reviewer` 接口」照旧，Claude 相关的费用估算不再适用，届时按所选供应商重新估算。
4. **复盘可以使用摊牌亮出的对手底牌。** 仍建议在输出里区分「决策当时可知」与「事后亮牌才知道」的信息，只是不再禁止模型引用后者。
5. **额度：暂不设上限，但在管理员设置里提供开关与数值**，管理员可随时动态调整（每人每日次数、全服每月 token 预算）。
6. **复盘面向有一定基础的玩家，写得专业**（使用位置、赔率、范围、SPR 等术语，不做入门讲解）。

### 0.8.0 相对第 4 节设计的出入

- 分页接口没有新开 `GET /v1/hands`，而是给已有的 `GET /v1/hands/recent` 加了 `before` 游标参数，旧客户端不受影响。
- 超时标记（`timed_out`）已随第 1 阶段一起记录；发两次的协商过程、加时卡不进入回放。
- 回放生成失败返回 `replay_unavailable`（422）并写 Error 日志；手号不存在或请求者不在其中统一返回 `hand_not_found`（404）。
- 步骤类型定为 blinds、action、street、runout、refund、showdown、settle（设计稿是 deal/blind/award）；时间轴不单独给 `toCall` 与 `note`，说明文字由客户端按步骤生成。
- 进度条没有按街打标记；控件在手机上分放左右两栏（说明在左、操作在右），不在底部。
- 自检只核对每名玩家的结束筹码；「输赢之和 + 抽水 = 0」由牌谱入库时校验，回放不再重复。
- 实现中发现并修复了几处既有缺陷：上一手结算未入账时，进观战、离开（含被请出、被移出）或等结算的离开者回房，都会让补做永远失败、牌桌开不了局；换座会让那一手的回放对不上座位。0.8.0 起换座与进观战在这个窗口里拒绝，离开与回房先补做结算。

## 9. AI 复盘的补充拍板（2026-09-23，0.9.0）

1. **大模型以 DeepSeek 为主，但接口按 OpenAI 兼容格式实现**：服务地址、模型名、密钥全部可配置，换任何兼容 OpenAI Chat Completions 的服务只改配置。提示词与效果以 DeepSeek 调优。
2. **开发期用真实模型调提示词**：密钥由维护者写进本机仓库根目录的 `.env`（已被 Git 忽略），只在本机测试时读取，不输出、不提交。
3. **分析范围：这一手 + 对手打法倾向**。倾向只从**请求者与该对手同桌打过的牌局**统计，只用公开动作（入池、加注、跟注、弃牌、摊牌），永远不含没亮过的底牌，不涉及请求者不在场的牌局。
4. **版本号 0.9.0**，稳定后再定 1.0.0。
5. **隐私：只改隐私说明，不做首次使用弹窗**。由管理员开通时自行告知对方。
