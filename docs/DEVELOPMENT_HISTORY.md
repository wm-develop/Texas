# 开发历程

本文把从最初选型至今的主要需求决策、实现里程碑和关键修复整理为一条可追溯时间线，用于解释“为什么项目现在是这样”，不替代当前状态、规则和协议文档。

早期按阶段 0～3 组织的六份清单文档（技术验证、规则与协议、可玩 MVP、牌桌可玩性、阶段 2 验收、上线准备计划）已于 2026-09-02 合并进本文并从仓库移除，原文可在 Git 历史中查到；其中「2～10 人位置表」已迁入[规则规格](TEXAS_HOLDEM_RULES_V1.md)。

## 1. 选型与范围确认

项目最初目标是让同一款德州扑克游戏运行在 Windows Web、Windows 客户端、Android、HarmonyOS，并在条件允许时兼顾 iOS。考虑维护者已有 Flutter、ArkUI/ArkTS 和 Kotlin 基础，最终选择 Flutter OH 作为客户端主体，Go 作为权威游戏服务。

核心边界随后确定为：

- 只服务希望快速组织牌局的熟人玩家，不做公开传播和陌生人匹配。
- 纯娱乐筹码，不接支付、不提现、不兑换现实资产。
- 单桌 2～10 人，横屏优先。
- 首版即包含牌桌文字聊天和 TRTC 自由麦语音。
- Flutter OH 使用 CPF-Flutter `oh-3.41.9-dev` 系列。

## 2. 阶段 0：四端技术验证

- 建立 Flutter OH 四端工程和 Go 服务骨架。
- 验证 WebSocket、TRTC UserSig、平台权限、横屏和本地存储。
- Android、Windows、HarmonyOS 使用 `tencent_rtc_sdk`，Web 使用仓库内 TRTC Web SDK 桥接。
- 完成 Android/HarmonyOS、Windows/HarmonyOS、Web/Android 的双向语音验证，并确认退出语音不会断开牌局连接。
- 处理 Android Gradle/JDK、Release 闪退、HarmonyOS 签名和白屏等工具链问题。

## 3. 阶段 1：规则与协议

- 完成 2～10 人无限注德州规则引擎、牌型比较、牌堆、主池/多层边池、平分与余数分配。
- 建立牌桌状态机、超时动作、请求幂等、`handId`/`tableRevision` 校验和协议消息外壳。
- 固定种子完成 100,000 手模拟，验证筹码守恒、牌唯一性和必然结束。
- 输出规则规格、WebSocket 协议和 TRTC 架构决策。

## 4. 阶段 2：可玩 MVP

- 接入注册登录、好友房、房间码、准备、座位和完整联机牌局。
- 增加事件序号、断线补发和按接收者裁剪的私人快照。
- 接入聊天、快捷语、表情、历史、本地屏蔽、语音成员和最近牌局。
- 完成 10 个独立 WebSocket 客户端连续 100 手验收。

牌桌可玩性随后持续补齐：

- 覆盖 2～10 人位置标识、本轮下注、倒计时、主/边池和摊牌。
- 增加七档比例金额、自定义滑块/数字输入、按小盲步长和正确的“加注至”语义。
- 修正翻前比例加注基数、最小再加注增量、筹码不足时只显示弃牌/All in 等规则细节。
- 增加每手两张 30 秒加时卡、两人局 60 秒、普通行动 30 秒和 10 秒自动准备。
- 多轮修复玩家框、下注筹码、公共牌和摊牌互相遮挡的问题。

## 5. 阶段 3：账户筹码与生产链路

- 增加账户总筹码、无支付虚拟充值、筹码流水、房主自定义盲注/最大带入、玩家自主带入和手间补码。
- 建立 PostgreSQL 迁移、生产仓储、事务、行锁和请求幂等；修复过早结算时空公共牌写入 `NULL` 导致弃牌失败的问题。
- 完成真实 PostgreSQL 集成测试、Docker 镜像、健康/就绪检查和单实例云端部署。
- 建立自建部署、生产迁移/回滚和四端构建文档；生产域名、密钥和签名始终留在本地配置中。
- 增加短期 Access Token、Refresh Token 自动轮换和会话撤销。

## 6. 账号治理与个人资料

- 通过注册页牌图标连续点击 10 次初始化服务器首位管理员，且服务端保证只能成功一次。
- 增加账号列表、批量创建/状态治理、软删除、密码重置、用户名/筹码修改、注册开关、在线/房间状态、强制离桌和持久化文字禁言。
- 增加个人信息页，用户可修改登录用户名、牌桌昵称和密码。
- 登录和注册页逐步改为适配手机横屏，补充输入格式和错误提示。

## 7. 深化牌桌社交与规则

- 房主离开后按加入顺序移交房主，最后一人离开才关闭房间。
- 结算后亮牌；弃牌玩家可私下申请查看仍参局玩家手牌。
- 空座直接换位，满桌时发起双方换位申请。
- 实现“发一次/发两次”的严格触发条件和两块公共牌独立结算。
- 增加聊天未读、语音单人静音、下注/过牌/弃牌/All in 音效，以及赞赏/嘲讽动画和音效。
- 创建房间取消预设人数，座位随玩家动态扩展至最多 10 人。

## 8. v0.1.1 移动牌桌重构

- 应用启动后在移动端全屏横屏显示。
- 手机牌桌将顶部房间/连接/语音信息移到侧边，释放纵向空间。
- 移除独立手牌区，将本人手牌和所有摊牌放入对应玩家框；发两次时对手手牌不再被公共牌遮挡。
- 重排 2～10 人玩家框，扩大可读区域并明确图层：玩家框高于公共牌，下注筹码高于玩家框，互动气泡最高。
- Android/HarmonyOS 通过原生 API 获取挖孔区域，不用固定像素猜测安全边距。
- HarmonyOS 使用自定义横屏数字面板，解决系统内置输入方式数字不全且难以滚动的问题。
- HarmonyOS 声明扩展为手机、平板、PC/二合一等设备。

## 9. v0.2.0 真机修复与发布规范

`v0.1.1` 之后的一轮真机联调暴露出八个只在多端同时在场时才会出现的问题，全部在 `v0.2.0` 修复：

- 牌局进行中有人加入会让整桌快照失败、服务端卡死；改为「待入座」观战，本手结算后入座。
- 弃牌后离开牌桌的玩家返还筹码被推迟到结算之后执行，避免破坏本手筹码守恒。
- HarmonyOS 开麦后音频路由被系统抢占，改为固定扬声器。
- 登录页与大厅页按实时窗口高度切换布局，软键盘弹出即触发重排、输入框失焦、键盘收回；改用不随键盘变化的窗口尺寸判定档位。
- 修复聊天面板、`private_view` 中文标签、发两次展示和换位申请的若干显示与条件问题。
- 换位不再要求牌桌坐满。

同一版本确立了发布规范：四端版本号统一为 `0.2.0`（HarmonyOS `versionCode` 按 `major*1000000+minor*1000+patch` 换算），四端应用图标统一重绘，Android Release 支持通过 `android/key.properties` 配置独立发布密钥。

## 10. 生产保障：备份、CI、限流与可观测性

- PostgreSQL 定时备份、归档校验、异地复制（腾讯云 COS）、恢复演练与静默失败告警，并在生产服务器实际安装验证。
- GitHub Actions：服务端 gofmt/vet/test 与 `-race`、客户端 analyze/test、shellcheck 与仓库卫生检查。
- 分层限流：登录/注册/刷新按 IP、密码错误按用户名、房间与钱包操作按用户、TRTC 凭证按用户、单 IP WebSocket 并发上限，配合 `TRUSTED_PROXIES` 可信代理解析。
- 令牌保护的 `/metrics`、账本对账定时任务、健康巡检与钉钉告警。
- 成员进出的属性测试（随机操作序列下校验快照可用与筹码守恒），并验证它能捕获已修复的回归。

## 11. 账号注销、隐私与审计

- 用户可自行注销：密码二次确认、必须不在房间内、钱包筹码整体转入创建最早的在用管理员并记 `account_deletion` 流水、原用户名可被重新注册、管理员不能自行注销。
- 注册页与个人信息页内置隐私说明，正文与 [隐私说明](PRIVACY_NOTICE.md) 同源。
- 管理审计查询界面：按类别、用户、房间筛选管理操作与账号变更。
- 语音加入/退出以 `voice.joined`/`voice.left` 审计事件持久化（含房间与离开原因，不含音频内容）。
- 举报功能经评估后不做——熟人私人牌局的定位下，它解决不了任何实际问题。

## 12. 结构清理与稳定性工程

- 删除协议中五个从无发送点的常量，以及恒不命中的 `revisionFromError` 与随之始终为 0 的 `ErrorPayload.CurrentRevision`。
- 牌桌页从 3180 行拆至约 805 行：组件分入独立文件，语音状态与命令抽入 `table_voice_controller.dart`，自动准备/自动补码/牌桌请求的判定与去重抽入 `table_automation_coordinator.dart`。两个控制器不接触 `BuildContext`，此前无法测试的规则现在有了直接覆盖。
- 24 小时稳定性观测脚本与 `texas_goroutines`、`texas_memory_heap_bytes`、`texas_process_start_time_seconds` 运行时指标，判定协程泄漏、内存增长与静默重启。
- 优雅停机：`SIGTERM` 后停开新局、取消自动准备、广播原因，等所有牌桌打完当前手再退出；客户端凭 `session.authenticated` 的 `serverInstanceId` 识别服务端重启，并明确提示上一手作废。
- 多实例与 Redis 经评估决定暂缓，理由、若要实施的约束与重新评估的触发条件见 [ADR-002](decisions/ADR-002-MULTI-INSTANCE.md)。
