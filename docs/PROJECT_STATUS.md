# 项目现状

> 状态基线：`main` / `v1.0.2`（2026-09-24）
>
> 本文描述当前代码已经做到什么、还没有做到什么。历史阶段记录保留在各阶段清单中；当历史规划与本文冲突时，以当前源码、自动化测试和本文为准。

## 1. 产品边界

“好友德州”是一套供熟人快速组织私人牌局的纯娱乐筹码德州扑克系统，不提供公开匹配、公开房间发现、真钱充值、提现、筹码交易或现实资产兑换，也不面向互联网公开传播。

- 客户端：Flutter OH，同一套 Dart 代码覆盖 Web、Windows、Android、HarmonyOS。界面语言固定为简体中文（`flutter_localizations`，`appLocale`）：Flutter 按界面语言给汉字挑后备字体，英文界面在 Windows 上会挑到日文字体。
- 服务端：Go 模块化单体，权威裁决牌局、会话、房间和筹码变化。
- 持久化：生产环境使用 PostgreSQL；本地可使用进程内仓储。
- 语音：腾讯云 TRTC，音频不经过游戏服务转发。
- iOS：架构未主动排除，但尚未纳入正式构建、签名和验收范围。
- 发布：GitHub Release 只发布源码标签，不直接提供各平台安装包。

## 2. 已交付能力

### 账号、钱包与管理

- 用户名和密码注册/登录、轮换式 Refresh Token、注销和会话撤销。
- 登录用户名、牌桌昵称和密码的个人资料修改。
- 登录态持久化：刷新令牌存在设备上（应用私有的 shared_preferences，明文；本项目不涉真钱，且 HarmonyOS 没有可用的安全存储适配），启动时自动换会话。移动端进程被系统回收后回来不必重新登录，牌桌路由本就按「有房间就进牌桌」，因此会直接回到原来那一桌；配合 0.5.0 的崩溃恢复，那一手也还在。登出、注销、服务端明确拒绝令牌时清除；**没网、超时、版本过旧一律不清除**，否则信号不好的地方启动一次就得重新登录。版本门禁仍在最前面判断，自动登录绕不过阻断页；恢复过程串了三个请求，因此加了 8 秒总超时——不设上限时服务端挂起会让玩家对着一个没有出口的转圈等一分半，而此前登录页是立刻出现的。超时只是放弃等待，底层请求不会被取消，因此用代次标记让迟到的结果不再改动界面：否则慢网络下玩家在登录页打字打到一半会被自己跳进大厅，甚至把他刚手动登录的账号覆盖成上一个。迟到轮换出来的新令牌仍会存下来（服务端刷新时会删掉旧会话，不存就等于丢了登录态），只是不激活界面。临时失败（没网、5xx）后回到前台会**静默**再试一次，不切回等待界面——触发这条路径的前提正是网络不好，玩家很可能正在手动登录，切界面会把他填的表单连输入框一起卸载掉。令牌的过期时间按 UTC 存，避免玩家换时区后一个有效令牌被当成过期清掉；轮换出来的新令牌一律等写入落盘再继续，服务端刷新时会删掉旧会话，写入没落盘就被系统回收等于丢了登录态。**Web 端一律不持久化**：那里的 shared_preferences 落在 localStorage，而浏览器常常是公用的，下一个打开页面的人会直接进入上一个人的账号；移动端的设备通常属于一个人，风险完全不同。Web 用户关掉标签页要重新登录，这是刻意的，第一帧也直接是登录页而不是等待界面。
- 牌局回放（0.8.0）：牌局记录里展开任一手，点「回放这一手」，像录像一样逐步播放：发牌与盲注、每名玩家的每次行动、发出每条街、全下后补发或发两次、无人跟注的退回、摊牌、分池，各是一步，可播放/暂停、上一步/下一步、拖动进度、切换速度。所有人都能回放自己打过的牌；**画面里只有本人的底牌，别人的底牌只在摊牌亮出之后才出现**（结算后自愿亮牌与私下看牌不算），这条裁剪在服务端完成，客户端拿不到没亮过的牌。时间轴由服务端 `internal/replay` 从牌谱推出（牌谱只存动作与结果，每一步的筹码、底池、本街投入都要重算），推完用牌谱记录的结束筹码逐人自检，对不上就返回 `replay_unavailable`、写 Error 日志，绝不给看一份算错的录像；未被跟注的退回与引擎结算用同一个分池函数。盲注此前不是动作，0.8.0 起牌谱记下盲注额与盲注座位（迁移 000013 从房间给旧牌谱补上盲注额；旧牌谱的盲注座位按引擎规则由庄位推出：两人时庄位下小盲），超时代为过牌/弃牌的动作带 `timedOut` 标记。画面复用对局的 `TableCanvas` 与同一套画布几何，外观与真实牌桌一致。随机属性测试用真实牌桌管理层在 2/3/6/9 人桌各打一百二十手（下注、加注、全下、真正由服务端代为行动的超时、发两次、弃牌后离开再回来、抽水；这些覆盖按落库的牌谱统计并逐项断言），从每位参与者视角回放每一手，要求自检通过、任何一帧都不出现看不到的底牌、推出来的盲注座位与引擎一致；并用故意改坏的生成器确认这些断言真的能失败。
- AI 复盘（0.9.0）：在回放页点「AI 复盘」，由大模型以教练视角点评本人在这一手里的每个决策（好 / 合理 / 有争议 / 失误，附理由与每一步的最佳行动，以及标明为估算的对手范围胜率、本次与最佳行动的 EV），并给出总评、要点、对手打法倾向和「结果回顾」；开头的牌局概况（人数、盲注、本人位置与底牌、各家码量）与每一步的底池、需跟注、所需胜率、牌力、对随机手牌胜率由服务端直接填写，不经过模型。**只对管理员开通的账号开放**（「服务器管理 → AI 复盘管理」逐个开关），玩家只能复盘自己打过的手；管理员可随时关掉总开关、设每人 24 小时次数上限与全服最近 30 天 token 总额（0 为不限，默认都不限）。模型走任何兼容 OpenAI `chat/completions` 的服务，默认 DeepSeek `deepseek-reasoner`，由 `REVIEW_*` 环境变量配置，没配 `REVIEW_API_KEY` 时整个功能不出现。服务端 `internal/review` 先用与回放相同的裁剪牌谱算好局面数据（底池、需跟注、底池赔率、有效筹码、SPR、成牌与最好的五张牌及其中用到的底牌、同花听牌、对随机手牌的蒙特卡洛胜率，种子由手号决定，可复现；本人筹码比对手投入少时另给「本人最多能赢到的底池」，赔率按它算），再交给模型只做判断，不让模型自己算数；对手倾向（入池率、翻前加注率、翻后激进度、摊牌率）只统计请求者与该对手同桌打过、且在这一手之前的手，只用公开动作（没超过当前最高投入的全下按跟注算）。本人在这一手里没行动过的，不给入口、服务端也拒绝（`review_no_decisions`）。发给模型的数据只有位置、筹码、牌与动作，**不含用户名、昵称、账号或房间号，也不含没亮过的底牌**；摊牌亮出的牌只放在单独的「事后」一节，提示词要求点评决策时不得使用。请求进 `hand_reviews` 表排队，由一个后台协程逐条处理（进程重启时把「进行中」放回队列；停机时做完手上那一条再退出，main 在排空牌桌的同一时限里等它），同一手同一提示词版本只分析一次、结果缓存，失败的可以重新发起且不占每人次数（token 照记入预算）；排队期间关总开关、收回权限或额度用完时不再调用模型；结果存库失败先隔几秒重试，一直存不进去就退一步记失败；实在连失败也记不上时，没有人在处理的「进行中」对玩家显示为失败、可以重新发起，不会一直转圈。模型输出不合格式（包括漏写结论或写了认不出的结论）时重问一次，结论的常见同义说法归一到四档，逐步点评只保留确实是本人决策的步骤。开发时用真实牌桌管理层让五种风格的机器人打两百多手，挑八类有代表性的手交给真实的 DeepSeek 复盘调过提示词（`tablemanager/review_live_test.go`，默认跳过，设置 `REVIEW_LIVE_ENV` 与 `REVIEW_LIVE_OUT` 才会运行并产生费用）。失败原因只以原因码（`model_error`、`invalid_output` 等）返回客户端，模型服务的报错原文只进日志。隐私说明同步写明了会发给大模型服务的内容。1.0.0 起：模型默认 `deepseek-flash`，打开思考模式并带 `reasoning_effort`（默认 `xhigh`，DeepSeek 映射为 `high`），附带由账号换算的匿名 `user_id`；结果里不再单独给「牌局概况」；打开复盘面板时若回放停在本人有点评的那一步，自动滚到这一步并高亮；提示词升级后先显示旧版结果并可「用新版重新分析」；管理员可给每人单独设 24 小时次数与同时进行上限（没设的跟随全局），服务端同时分析的条数由 `REVIEW_WORKERS` 配置；DeepSeek 返回 429、5xx、超时时隔 30 秒、2 分钟自动重试共三次，返回 402（余额不足）、401（密钥无效）时排队中的一并记失败、5 分钟内拒绝新请求并在管理页提示。分析完全在服务端进行，玩家离开回放、去打牌或关掉客户端都不会打断，结果持久保存。1.0.1 起：牌局记录里本人已有复盘结果（任意版本）的手带「AI 已复盘」标识（`GET /v1/hands/recent` 的 `reviewedHandIds`，现在用不了复盘时不给）；提示词 v2 要求翻前平跟大盲直接写 limp，不译成「跛入」。1.0.2 起：复盘面板最下面有「复制复盘结果」与「复制提示词和结果」两个按钮（面板宽时并排、窄时上下排），后者向服务端取这一手按当前版本发给模型的系统提示词与数据（`GET /v1/hands/{handId}/review/prompt`，与分析共用 `promptFor`，一字不差）。
- 牌局记录（原「最近牌局」）：大厅工具栏的时钟图标点开，列出本人参与过的牌局，每页 20 手，可往前翻页（游标为上一页最后一手的手号，按 `(ended_at, hand_id)` 排序，不重复不遗漏）。每一手是一屏读完的牌谱：盈亏、公共牌（发两次分两行）、各家座位与筹码变化、按街的动作过程；对手盖着结束的牌显示「未亮牌」。牌面与牌桌共用四色和自绘花色。
- 观战位：房间成员可不占座位地观战，最多 10 人。付看牌费（默认 10 个大盲，房主可设 0～100，0 为免费）后能看到本手所有参与者的手牌，费用在**发牌前**收取并平分给即将参与的上桌玩家（余数从庄位起顺时针逐枚）；余额不足则本手不收费也不给看牌。看牌权一律在开局时发放（免费模式也是），手间或中途进入者看不到已结束/进行中的那手。切换在手间立即生效，牌局中只记意向、手结束后应用；上桌必须有筹码。房主可分别关闭观战者的语音/文字/表情，可随时移出观战者。右上角「X/10（OB: Y）」点开房间名单。手牌按接收者裁剪，普通玩家永远拿不到别人的牌。
- 弃牌确认：轮到自己且可以过牌时点「弃牌」先弹窗确认（能免费看下一张牌却弃牌几乎总是误触）；需要跟注时弃牌是正常决策，直接提交。弹窗期间若已超时轮到别人，确认也不会把弃牌打到别人的回合上。
- 赞赏/嘲讽气泡从玩家框底部向上飘，全程留在玩家框的竖向范围内；此前从框中心上方起飘，顶排座位的气泡一出现就在画布外被裁掉。
- 四色牌：黑桃黑、红桃红、方块蓝、梅花绿，公共牌与玩家框小牌同一套。**花色是自绘图形（`SuitGlyph`），不是字符**：♠♥♦♣ 在 Android / HarmonyOS 上会被系统彩色 emoji 字体接管，文字颜色对它们不起作用，只染得到点数。玩家框小牌一律「点数在上、花色在下」居中（一行文字时「10」放不下会折成靠左两行），尺寸 30×36（再高会在观战者看别人座位那一支溢出）。
- 玩家框里不再显示行动倒计时或任何「轮到谁」的文字：轮到谁由高亮边框表示，倒计时只在公共牌区显示一处。
- 弹窗里的可滚动内容区一律用 `DialogScrollArea`，高度按屏幕真实可用空间算：OpenHarmony 那版 Flutter 不会像上游那样把弹窗内容压到剩余空间，写死「屏幕高度 × 70%」会让最后一项永远滚不到（鸿蒙手机上房主看不到「房间管理」、管理员看不到「打开服务器管理」）。
- 房间管理里的看牌费输入框改为与补码弹窗同款的整行带标签输入，不再挤在说明文字旁的小格里（鸿蒙数字面板入口自带浮动标签，小格里比例不对）。
- 房主房间管理：手间可把成员移出房间（复用玩家自己离桌的路径，筹码照常返还；牌局进行中拒绝；管理员不可被移出），以及临时关闭房间入口（只挡新加入者）。任何成员都可查看本房间净胜负，并在客户端本地按自定比例换算金额，服务端不存储也不传输任何金额。净胜负 = 离桌返还 + 桌上筹码 − 累计带入；桌上筹码取自成员表，只在结算时更新，因此牌局进行中若本人**已弃牌**，客户端会把本手已投入底池的筹码从桌上筹码与净胜负中扣掉并单列一行——那笔钱已经输掉了，再算成自己的会虚高。没弃牌时归属未定，照常算在桌上；手间不扣，成员表那时已经扣过。
- 用户自行注销账号：密码二次确认、须不在房间内、钱包筹码整体转入最早的在用管理员并记 `account_deletion` 流水、原用户名可再注册；注册页与个人信息页内置隐私说明。
- 抽水（0.7.0）：只有管理员能按房间设置，房主不能；新房间默认不抽。规则五项：开关、比例（万分比，上限 1000 即 10%）、封顶筹码（0 为不封顶）、翻后加抽开关、加抽筹码（不超过一个大盲，不受封顶限制）。基数是**退还无人跟注部分之后**的底池；比例部分向下取整后再封顶；「发出翻牌」按手结束时公共牌不少于 3 张判断，全下后补发的牌面也算；底池不足两个大盲时不加抽（短码盲注位全下的小底池会被一个大盲的加抽整个抽走）；一手只抽一次（发两次也一样），有边池时按各池大小分摊、零头用最大余数法逐枚补齐——从主池起依次扣会让只能争主池的短码玩家替边池付掉全部抽水。修改从下一手起生效——引擎只在两手之间接受新规则，进行中的一手按开局时的规则结算，崩溃恢复出来的也一样（规则与收款人随引擎状态一起落盘）。抽走的筹码打进**最早创建的在用管理员**的钱包，与该手结算同一事务，多一条 `rake` 流水（`request_id` 为 `rake:<handId>`）；没有管理员或未接钱包时这一手不抽，而不是抽了没处放；收款的管理员自己就在这个房间里（升级前就坐着的存量）时也不抽。设置接口只写 `rooms` 的抽水几列（`SaveRake`），不走整体 `Save`——后者会按旧值重写成员行，而管理员改规则时牌局多半正在进行。向下取整意味着玩家合计输掉的恰好等于抽走的整数，守恒式从「输赢之和为 0」改为「输赢之和 + 抽水 = 0」，引擎、牌谱校验与钱包事务三处同时校验。规则变更写审计（`admin.rake_changed`），并以 `kind=system` 的聊天消息在房间里公告具体比例与封顶，玩家伪造不了这种消息，客户端不受屏蔽名单影响、单独成样式显示，聊天没开着时另给一条提示；每手抽了多少写在结算区与「最近牌局」。公告会被后面的聊天刷走，因此快照带 `rake`（房间当前规则），牌桌信息栏常驻显示；加入房间前的预览同样带 `rake`，带入窗口里写明。接口先公告、随即补发一次快照（信息栏立刻更新，不必等下一个牌局事件）、最后记审计；规则已落库时审计写失败不回错误（那会让管理员以为没改成，重试时规则没变也不会再记），而是照常回 200 并写一条带完整参数的 Error 日志。建房不限盲注与带入，所以比例与分摊的乘法都按不会溢出的方式算（分摊用 128 位乘除）：溢出后各池之和仍等于总抽水，三处守恒校验都发现不了，却会把筹码从一个池挪到另一个池。管理员账号不能创建或加入房间（`admin_cannot_play`，服务端拒绝，客户端大厅同样拦住并说明）：收抽水的人不能同时坐在桌上。看牌费不抽水。后台「抽水管理」页列出开着的房间及规则、按房间累计（含已关闭房间）与合计，换算比例只在本机计算。接口：`GET /v1/admin/rooms`、`POST /v1/admin/rooms/{roomID}/rake`（五个字段必须传齐，漏传不会被当成关闭）、`GET /v1/admin/rake`。
- 娱乐筹码钱包、无支付虚拟充值、不可变流水、入桌带入、手间补码和离桌返还。弃牌后中途离开时成员记录保留到本手结算，结算后再退还并移出（桌上筹码就记在成员记录上，提前删除会让筹码凭空消失——线上出过这个事故）；离桌退还的幂等编号按「每一次入座」区分（入座时间由房间服务保证严格递增），同一房间可以反复进出。结算落盘中途失败（例如退还时数据库出错）会在下一次有人准备时整段补做，筹码只写一次、不会盖掉期间的补码；**补做成功之前不开下一手**，否则引擎继续发牌而账户一分不记（线上一个房间这样打了 46 手）。结算失败写 Error 日志，并向全桌广播快照。同步引擎成员的路径（加入、准备、快照）在牌桌锁内取成员表；上一手没入账时也拒绝补码（`settlement_not_persisted`）：此前先取再上锁，自动准备到点与有人离开撞在同一瞬间会把刚离开的人加回引擎成「幽灵座位」，之后每手结算失败。0.8.0 起，这个「上一手没入账」的窗口里：换座、接受换座、进观战一律拒绝（回 `settlement_not_persisted`）；有人离开（包括被房主请出、被管理员移出）时先把上一手补做完再走；等结算的离开者这时回到原房间，同样先补做、完成他的离开，再让他像新玩家一样重新带入。此前进观战或离开会把人移出引擎，补做时守恒校验永远失败、牌桌再也开不了局；离开者回来则会按这一手之前的筹码被加回引擎，之后每一手都结算失败。从观战上桌不受影响（新座位不在上一手的结算名单里）。已知边界：待离开者在本手结算前仍占着座位与成员名额；若服务端崩溃且那一手没能恢复，「待离开」标记随之丢失，他会变回普通成员（筹码完好），需要本人再点一次离开或由房主移出，否则他不会准备、下一手开不了。
- 首位管理员一次性初始化；注册开关、账号创建/停用/恢复/软删除、批量操作、密码重置、用户名和筹码调整。
- 管理员查看在线状态、当前房间并强制离桌；持久化文字禁言和管理审计，客户端「审计记录」页可按类别/用户/房间查询管理操作、账号变更与语音加入/退出元数据。

### 房间与牌局

- 六位房间码、可选房间密码、动态 2～10 人牌桌，创建时不预设人数。
- 房主标识与按加入顺序自动移交；最后一名成员离开后房间关闭。
- 2～10 人无限注德州扑克：位置、按钮/盲注轮转、四条下注街、主池/边池、平分和余数分配、摊牌与结算。
- 小盲最低 10、大盲最低 20 且为小盲整数倍；普通下注/加注和自定义滑块按小盲整数倍，All in 可为非整倍数。
- 1/4、1/3、1/2、2/3、满池、1.2 倍超池、All in 和自定义额度；比例加注以完成跟注后的底池为基数。
- 普通行动 30 秒；仅剩两名未弃牌玩家时 60 秒；每手每人两张 30 秒加时卡。
- 每手结束后 10 秒自动准备（发两次结算为 15 秒，留足两块牌面的展示时间），允许主动取消；筹码为零时要求补码。
- 牌局进行中加入房间的新玩家以待入座状态观战，本手结算后自动入座；已弃牌或本手未参局的玩家可随时离桌，弃牌者的剩余筹码在本手结算后幂等返还钱包。
- 结算后主动亮牌、弃牌后的私下看牌申请（目标可以是仍参局或已弃牌的玩家）、点击其他玩家发起双方确认的换位申请。
- 申请偏好与拒绝范围：每位玩家可在设置里关闭「允许别人申请换座 / 私下看我的牌」（房间内有效，离开即重置）；拒绝换位可选「不再接受此人」（本房间内），拒绝看牌可选「本手不再接受此人 / 任何人」；对方同意看牌后本手不能再向其申请；申请者通过只发给本人的 `table.request.declined` 收到区分范围的提示，服务端当场拒绝的走对应错误码。偏好与屏蔽只存在内存与进行中的牌桌状态行里：牌局进行中崩溃恢复能保留，**手间重启（包括正常发版）会把所有人的偏好与换座屏蔽重置为默认**，玩家重新设置即可；要跨发版保留需把偏好挪进房间成员表（新迁移），暂未做。
- 满足“两名未弃牌玩家、至少一人全下、对手已跟注或全下、后续无需行动”时协商发一次/发两次；只有双方都选两次才运行两块公共牌。

### 实时、聊天、语音与交互

- WebSocket 鉴权、请求幂等、牌桌序号、缺口补发、私人快照和断线恢复。
- 文字、快捷语、表情、历史恢复、收起状态未读提醒、本地屏蔽和服务端禁言。
- TRTC 主动加入、自由麦、成员/开麦/说话状态、单人静音和播放音量。
- 下注、过牌、弃牌、All in 音效；点击头像发送赞赏/嘲讽动画和音效，带服务端冷却。

### 多端体验

- 全端横屏和应用级全屏；Windows 可缩放窗口，手机牌桌采用独立响应式布局。
- 本人手牌与摊牌直接显示在玩家框中，支持两块公共牌时仍可看到对手摊牌。
- 图层顺序为公共牌背景、玩家框、玩家本轮下注筹码、好友互动气泡；筹码和互动不会被玩家框遮挡。
- Android 使用 `WindowInsets.displayCutout`、HarmonyOS 使用 `getWindowAvoidArea(TYPE_CUTOUT)`，通过 MethodChannel 补充原生挖孔安全区。
- HarmonyOS 提供横屏数字输入面板，避免系统数字输入区域无法滚动或遮挡内容。
- HarmonyOS 模块声明支持手机、平板、PC/二合一等设备类型。

## 3. 当前架构

```text
Flutter 客户端
  ├─ HTTPS REST：账号、资料、钱包、房间、历史、管理、TRTC 凭证
  ├─ WSS：牌桌动作、快照、聊天、语音状态和好友互动
  └─ TRTC：独立音频媒体通道

Go 单实例游戏服务
  ├─ transport：HTTP/WebSocket、鉴权、CORS/Origin、安全头
  ├─ room/tablemanager：房间成员、权威牌桌和事件广播
  ├─ holdem：纯规则、牌型、底池、状态机
  ├─ account/bankroll/history/chat/ledger：业务仓储接口
  └─ postgres：生产仓储、事务与迁移

PostgreSQL：账户、会话、钱包、房间、手牌、行动、结算、聊天和审计
TRTC：牌桌语音
```

客户端当前使用 Flutter 自带的 `StatefulWidget`、`ChangeNotifier` 和显式 service/client 对象组织状态，没有引入 Riverpod 或 `go_router`。服务端为模块化单体；运行中的房间/牌桌和在线状态仍由单个进程持有。

实时协议是**快照驱动**的：牌局状态变化统一通过按接收者裁剪的 `table.snapshot` 下发，模式为"给发起者一条定向回执 + 向全桌广播一轮个性化快照"。除快照外只有聊天、玩家互动和语音状态三种共享广播事件。早期设计中的细粒度手牌事件（`table.hand.started`、`table.board.dealt`、`table.action.required` 等）从未实现，协议文档已于 2026-09-01 按源码校正。

## 4. 数据库版本

当前共有十组迁移：

1. `000001_phase3_core`：账户、会话、钱包、房间、手牌、聊天和账本基础表。
2. `000002_admin_console`：角色、账号状态、注册开关和管理审计。
3. `000003_admin_account_management`：管理员账号与钱包治理。
4. `000004_chat_moderation`：持久化文字禁言。
5. `000005_runout_boards`：发两次公共牌和分池结算。
6. `000006_dynamic_room_capacity`：创建房间不预设人数，容量动态扩展至 10 人。
7. `000007_account_deletion`：账本 `reason` 约束增加 `account_deletion`，用于账号注销时钱包整体转入管理员。
8. `000008_room_join_lock`：房间增加 `join_locked`，房主可临时关闭入口。
9. `000009_client_version_gate`：`server_settings` 增加 `minimum_client_version`，管理员可随时调整客户端版本门槛。
10. `000010_spectators`：`rooms` 增加观战位设置四列；`room_members` 增加 `spectating`，座位号允许为 0，座位唯一约束改为只对真实座位生效。
11. `000011_table_states`：新增 `table_states`，保存进行中牌局的状态快照供崩溃后恢复；每房间至多一行，手结束即删除，随房间级联删除。
12. `000012_rake`：`rooms` 增加抽水规则五列（默认不抽）；`hands` 增加 `rake`；账本 `reason` 约束增加 `rake` 并为按房间汇总建部分索引；聊天 `kind` 约束增加 `system`。回滚前提是库里没有 `rake` 流水——账本不可变，有了就不能回滚。
13. `000013_hand_replay`：`hands` 增加大小盲额与大小盲座位四列（盲注额从房间补给旧牌谱，座位旧牌谱为 0）；`hand_actions` 增加 `timed_out`；为牌局记录翻页建 `hands(ended_at, hand_id)` 索引。
14. `000014_hand_review`：AI 复盘的全局设置单行表 `review_settings`（默认开着、不限额度）、开通名单 `review_access`、复盘任务与结果 `hand_reviews`（每人每手每个提示词版本一行，结果为 JSONB，记录输入/输出 token 数）。
15. `000015_review_limits`：`review_settings` 增加每人同时进行上限（默认 0 不限）；`review_access` 增加按人单独设的每日次数与同时进行上限（NULL 表示跟随全局）；`hand_reviews` 增加自动重试次数与下一次重试时间。

生产环境必须先运行 `migrate up`，再启动对应版本游戏服务。服务启动会校验迁移版本和 SQL 校验和。

## 5. 已有验证证据

- 规则引擎固定种子模拟 100,000 手，筹码守恒且每手必然结束。
- 牌桌管理层成员生命周期属性测试：5 组固定种子、每组 400 次随机操作（入房、离桌、准备、行动、断线、重连、补码、换位、亮牌），每步之后断言全体成员快照均可生成、筹码守恒、无负余额。该测试已验证能复现并拦截“牌局进行中加入导致全桌快照失败”这类缺陷。
- 10 个独立 WebSocket 客户端连续完成 100 手，生成 1,000 条玩家账本记录并逐手守恒。
- Go 单元、集成和真实 PostgreSQL 集成测试已通过；Flutter 静态检查和单元/Widget 测试已通过。
- Web、Windows、Android Release 和 HarmonyOS 签名 HAP 均曾成功构建。
- Web/Android/HarmonyOS 三端牌局以及 Web、Windows、Android、HarmonyOS 间多组 TRTC 双向语音已实机验证。
- Android Release 曾因 R8/资源裁剪启动闪退，当前构建已关闭两者并验证可启动。
- HarmonyOS 曾出现白屏和数字输入问题，当前依赖/启动链及自定义数字面板已修复并实机确认。

以上是历史验证基线，不代表每次提交自动保持通过。每次发布仍应按目标平台重新执行测试、构建和真机冒烟。

2026-09-01 交接复核时，`go test ./... -count=1`、`go vet ./...`、`flutter analyze` 和 48 项 Flutter 测试均通过。第一次 Go 全量运行曾出现 `TestWebSocketReconnectRestoresCurrentHandAndPrivateCards` 的一次时序性失败；该用例随后连续运行 3 次通过，全量测试再次运行也通过。

同日交接接手方独立复跑 `go vet ./...` 与 `go test ./... -count=1` 全部通过，未复现上述抖动（`internal/transport` 包耗时约 34 秒）。该用例仍应视为观察对象：若再次出现，应检查等待条件与连接关闭的同步，而不是长期依赖重跑掩盖问题。

## 6. 明确未完成或有风险的部分

- Redis 尚未接入；不支持多游戏服务实例、权威牌桌租约、实例故障自动接管或无损热迁移。多实例已在 [ADR-002](decisions/ADR-002-MULTI-INSTANCE.md) 中评估并决定**暂不实施**：收益主要落在崩溃可用性且只是部分，解决不了「部署要停牌局」这个真实痛点，而引入 Redis 会把一个单点变成两个单点。该 ADR 同时写明了若要实施必须满足的约束、验收标准与重新评估的触发条件。
- 运行中的牌桌状态主要在内存中。数据库保留业务记录，但服务进程异常退出后不能完整恢复进行中的一手牌。
- 备份、恢复演练、账本对账、健康巡检与告警均已提供可执行方案（`deploy/backup/`、`deploy/monitor/`，见[备份恢复指南](BACKUP_AND_RESTORE_GUIDE.md)与[运行保障指南](OPERATIONS_GUIDE.md)）；2026-09-01 生产服务器已全部安装并验证：备份定时任务、异机复制、恢复演练、对账定时任务、健康巡检，以及钉钉告警通道（手动触发与 OnFailure 链路均实际收到消息）。24 小时故障注入尚未做。
- `/metrics` 增加 `texas_goroutines`、`texas_memory_heap_bytes`、`texas_process_start_time_seconds` 三项运行时指标，供 `deploy/monitor/texas-soak.sh` 判断协程泄漏、内存增长与静默重启；脚本启动时会核对指标名，服务端改名后立即失败而非静默记 0。
- 优雅停机已实现：`SIGTERM` 后停开新局、取消自动准备、广播 `draining` 快照并等待所有牌桌到达手间空档（`SHUTDOWN_DRAIN_TIMEOUT_SECONDS`，默认 120 秒），部署时须 `docker stop -t 150`。客户端凭 `session.authenticated` 的 `serverInstanceId` 识别服务端重启。**进行中的手已能跨重启恢复**（0.5.0，需接入 PostgreSQL）：引擎每次推进后把完整状态写入 `table_states`，手结束即删除，重启后第一个回到房间的人触发恢复并重新安排行动倒计时；状态版本不符、内容自相矛盾或盲注被改过时放弃恢复，退回「本手作废」的旧行为。客户端据此改为等重连后的第一条快照再判断：手号不变即恢复成功，不再提示作废。见协议文档 6.8。
- 2026-09-03 多人试玩暴露并修复三处连接状态缺陷：同一用户的旧连接关闭会把在线玩家标为断线并取消准备（现在只有当前生效连接的关闭才算离线，旧连接以关闭码 4001 被主动关掉）；牌局中途加入者结算后一律以断线入座（现在按真实在线状态入座）；动作被拒后客户端请求快照却只收到空的 `replay.completed`（现在显式请求一律回完整快照）。客户端另加动作回执 5 秒看门狗、`system.error` 也放开按钮、自动准备 3 秒后重试，发牌动画改用单调时钟。
- 屏幕圆角与鸿蒙全屏：圆角不属于挖孔也不属于系统栏，两套 inset 都不含它，却会切掉贴顶控件的一角（安卓手机右上角的聊天按钮）。Android 用 `WindowInsets.getRoundedCorner`（API 31+）上报四角半径，顶部两栏据此下移，已被安全区推开的部分不重复计；鸿蒙无对应接口且实测正常，返回 0。另外鸿蒙的 `FlutterAbility` 并不会自动全屏——平板上一直顶着系统状态栏，现在在 `onWindowStageCreate` 里显式做沉浸式布局并隐藏状态栏，只隐藏状态栏、保留手势导航指示器（一起隐藏会让避让区返回 0，界面不再让开，底部按钮又变得点不动）。**平板真机待验证。**
- 平板横屏右栏按钮被裁掉/点不动：一是右栏可用高度不足时下注区被直接裁掉，改为贴底可滚动；二是手势导航条压在屏幕底部、落在那片区域的按钮触摸归系统，原生避让区查询在挖孔之外补上导航条（HarmonyOS `TYPE_NAVIGATION_INDICATOR`、Android `navigationBars()`），Flutter 侧再用 `viewPadding`/`systemGestureInsets` 与已消费 padding 的差值兜底。**平板真机待验证。**
- HarmonyOS 开麦后听不到远端（真机复现并定位）：真因是**牌局提示音**，不是 TRTC 角色切换。鸿蒙音频焦点是应用级的，`audioplayers` 的 `FocusManager` 每次播放前调用 `setAudioSessionScene(AUDIO_SESSION_SCENE_MEDIA)` 并以 `CONCURRENCY_DEFAULT` 激活音频会话，该模式独占物理输出通道并压制应用内其他音频流，于是每有玩家动作播一声提示音，系统音量类型就被改成媒体音量（音量条话筒变喇叭）、TRTC 通话流被压制。用户实测无动作时静置一分钟音量类型始终是话筒，独立佐证了这一点。真机排除法走了四轮：①语音中静音（可用但没提示音）；②交给 TRTC `startPlayMusic` 走通话流（不掐语音，但音量偏小、有延迟断续——那条链路是给背景音乐用的）；③把插件并发模式改成 `CONCURRENCY_MIX_WITH_OTHERS`（**实测无效**，证明致命的是 `setAudioSessionScene(MEDIA)` + `activateAudioSession` 这套会话切换本身，不是并发模式）；④当前方案：鸿蒙原生 `SoundPool` 通道（`com.texas.game.poker_client/table_sound`），系统为短音效提供的低时延通道，完全不经过 `AudioSessionManager`，usage 取 `STREAM_USAGE_MUSIC` 时按官方说明为混音模式、不打断其他音频。提示音字节先落盘（SoundPool 按路径播放，单个需 <1MB）。四种方式保留为 `HarmonyVoiceSoundStrategy`，改一个默认值即可切换。原生通道不可用时安静跳过，等同于静音，绝不回退到会掐断通话的路径。Android/Windows 行为不变。**待真机验证。**
- HarmonyOS 语音仍使用音频通话场景、以主播身份进房且不切换角色（上一轮改动）：让所有人全程处于通话音量，与上面的修复叠加保留。
- 客户端版本门禁：最低版本存在数据库 `server_settings.minimum_client_version`（迁移 000009），管理员在客户端的服务器管理页调整，进程内原子缓存随之刷新，**立即生效且不需要改环境变量或重建容器**——只更新客户端的发布不必登服务器。为 0 时完全不启用。版本号用 `major*1000000 + minor*1000 + patch` 编码，四端与鸿蒙 `versionCode` 同一套，由 `app_version_test.dart` 锁住 Dart 常量 / pubspec / `app.json5` 三处一致。客户端每次请求带 `X-Client-Version`（WS 走 `clientVersion` 查询参数，浏览器不能设自定义头），门禁包在整个 mux 外层，WS 升级一并覆盖；过旧返回 426，客户端进入不可跳过的阻断页。登录、刷新令牌与「调整门槛」这三条路径豁免门禁，作为逃生通道：否则门槛设得比管理员自己的客户端还高时会把自己锁死。`GET /v1/client/version` 无需鉴权；返回 404 说明服务端才是旧的，此时客户端不自锁。
