# 好友德州 v1.0.0

在 0.9.0 AI 复盘的基础上补齐：按人设置的额度与同时进行上限、大模型报错时的自动重试与暂停、打开复盘时定位到当前这一步、提示词升级后保留旧结果，并把模型换成打开思考模式的 `deepseek-flash`；同时修正了「对手都已全下后仍能加注」的规则问题。**数据库、服务端、客户端三处都要更新**，环境变量有新增，顺序见文末「升级须知」。

## 玩家看到什么

- 回放停在自己操作过的某一步时点「查看 AI 复盘」，面板会**自动滚到这一步的点评并高亮**（标「当前步」）；停在别人的步上时从总评开始看。
- 复盘结果**持久保存**：分析过的牌局下次打开回放直接能看，不需要重新分析，也不占次数。以后复盘升级了，旧的结果仍然先显示出来，上面有「用新版重新分析」按钮。
- **分析在服务器上进行**：点了之后可以离开回放、回大厅、去打牌，甚至关掉客户端，都不会打断；下次打开这手回放就能看到结果（还没分析完的会接着显示「分析中」）。
- 大模型服务繁忙或超时时会**自动重试**，面板写明「正在自动重试（第 N 次）」；三次都不行才提示失败，可以稍后重新分析，失败的不占次数。
- 复盘面板不再单独列「牌局概况」，其余五部分（总评、逐步点评、要点、对手倾向、结果回顾）不变。
- **手机上的回放页两侧栏不再显得过大**：说明栏与控制栏和牌桌一起缩放，字号、按钮尺寸与打牌时的牌桌页一致；左上角的标题拆成「牌局回放」和「房间号」两行，不再显示成「牌局回...」。
- **对手都已全下时只能跟注或弃牌**：此前还会出现加注按钮，加上去的筹码没人能跟、最后原样退回，牌谱与回放里却留下一个没有意义的「加注」。筹码结算一直是对的。

## 管理员看到什么

- 「AI 复盘管理」的全局设置多了「**每人同时进行**」（排队中加分析中的条数，0 为不限，默认不限）。
- 名单里每个已开通的人可以点「**单独额度**」，分别设「24 小时内次数」和「同时进行」；留空表示跟随全局设置，0 表示不限；对话框里的「都跟随全局」一键恢复（鸿蒙的数字面板不能提交空值）。列表里直接显示每人当前生效的额度，改动记入审计记录。
- 顶部的模型状态显示型号与「同时分析 N 条」。大模型账户**余额不足**或**密钥无效**时变成红色提示，并写明发生时间。

## 实现要点

- **每人的额度**：每日次数与同时进行上限都是「单独设的优先，没设的用全局」。同时进行数的是这个人排队中与分析中的条数，发起时超出就提示「你同时在分析的牌局已达上限」。
- **服务器的并发**：`REVIEW_WORKERS`（默认 2，至少 1、没有上限）个工作协程同时分析，所有人共用。DeepSeek 的并发上限是按账户算的（deepseek-flash 为 2500），远大于熟人局的需要，实际的约束是费用和排队时间，所以不做成按人的设置。
- **DeepSeek 报错的处理**（按官方错误码）：
  - 429（请求速率上限）、500、502、503、504、网络错误，以及以 200 返回但 `finish_reason` 为 `insufficient_system_resource`（资源不足中途停止）/ `aborted`、或排队后只回空白就断开：临时故障，隔 30 秒、2 分钟自动重试，共调用三次，期间状态仍是排队中；三次都不行记为「服务繁忙」。
  - 超时：一共最多调用两次（与繁忙的重试共用次数，之前已经因繁忙重试过就不再重试）。思考模式下一次生成就可能超过时限，多试几次只会让玩家白等；仍超时记为「分析超时」，提示管理员调大 `REVIEW_TIMEOUT_SECONDS`。超时的调用拿不到 token 用量，不计入全服预算。
  - 402（余额不足）、401（密钥无效）：全局故障，这一条与所有排队中的都记为失败（再调用也只会失败，还白白让玩家等），5 分钟内拒绝新的复盘并在管理页提示；5 分钟后放行，下一次调用成功就恢复。
  - 400、403、422（请求格式、权限或参数错误）：只影响这一次，记为失败并写服务端日志。403 不当全局故障：兼容服务与中转常用它表示地区限制或没有某个模型的权限。
  - 失败原因只以原因码返回客户端，每种都有中文说明；模型服务的报错原文只进服务端日志。
- **`user_id`**：附带一个由账号换算的匿名编号（同一个人每次相同，反推不出账号），DeepSeek 用它做按用户的内容安全与缓存隔离。它不会提高普通账户的并发上限（按 `user_id` 的调度隔离只对升级账户生效），所以不当作限流手段。只在 DeepSeek 上默认发送，其他兼容服务可能不认识这个字段。
- **模型与思考模式**：默认 `deepseek-flash`，在 DeepSeek 上请求里带 `"thinking": {"type": "enabled"}` 与 `"reasoning_effort": "xhigh"`。按 DeepSeek 文档，`xhigh` 会被映射为 `high`（思考模式默认就是 `high`），最高档是 `max`；都可以用环境变量改。此前配置的 `deepseek-reasoner` 在 DeepSeek 那边实际返回的也是 `deepseek-flash`。这两个字段与 `user_id` 都是 DeepSeek 的扩展字段，地址不在 deepseek.com 上时默认不发——0.9.0 用千问、OpenAI 或中转服务的搭建者升级后不会因为多出不认识的字段而每条都失败，要用时显式设置。
- **旧版结果**：结果按提示词版本缓存。当前版本没分析过时，接口返回最近一次完成的旧版结果并标 `outdated`；「用新版重新分析」按新版排队，占一次次数。新版排队、分析中或失败时，返回里带着旧版结果（`previous`），面板下方接着显示；重新分析被拒（额度用完等）时旧结果也照常显示，错误写在上面，「重试」会再次发起。
- **没人处理的「进行中」**在多个工作协程下同样能认出来：每个协程登记自己手上的那几条，领取与登记在同一把锁里。

## 接口与协议

- 新增 `POST /v1/admin/review/limits`（`userId`、`dailyLimit`、`maxInFlight`，`null` 跟随全局）。
- `POST /v1/admin/review/settings` 多了 `maxInFlightPerUser`（不传时保持原值）；`GET /v1/admin/review` 的名单带每人额度，另有 `workers` 与 `modelHealth`。
- 复盘对象多了 `attempts`、`nextAttemptAt`、`outdated`、`previous`，结果里去掉了 `situation`。
- 新错误码：`review_in_flight_limit`（429）、`model_insufficient_balance` 与 `model_unauthorized`（503，冷却期内拒绝新请求）；新失败原因码：`model_busy`、`model_timeout`、`model_insufficient_balance`、`model_unauthorized`。
- 新审计事件：`admin.review_limits_changed`。
- 详见 `docs/WEBSOCKET_PROTOCOL_V1.md` 7.8。

## 升级须知

1. **备份后先跑数据库迁移 `000015_review_limits`，再启动新服务端。** 迁移只给三张复盘表加列与一个索引，不改动已有数据。从 0.8.x 直接升级的，`migrate up` 会先跑 0.9.0 的 `000014_hand_review` 再跑 `000015`，同时按 `v0.9.0.md` 的升级须知配置 `REVIEW_API_KEY` 等变量。
2. 服务端环境文件：按 0.9.0 的示例写了 `REVIEW_MODEL=deepseek-reasoner` 的，改为 `deepseek-flash`（或删掉这一行用默认值），新默认值对显式写了旧名的配置不生效；按需加 `REVIEW_THINKING`、`REVIEW_REASONING_EFFORT`、`REVIEW_SEND_USER_ID`（这三项在 DeepSeek 上默认为 `enabled`、`xhigh`、开，其他服务默认不发）与 `REVIEW_WORKERS`（默认 2）。含义见 `.env.example` 与 `docs/SELF_HOSTING_GUIDE.md`。**值不要加引号、不要在行尾写注释**：`--env-file` 会把它们原样算进值里，`REVIEW_WORKERS=2 # 注释` 会让迁移和服务端都因配置不合法拒绝启动；`REVIEW_API_KEY` 加了引号则会在调用时被判为密钥无效。
3. 更新服务端并重启。0.9.0 客户端仍能发起和查看复盘，只是没有当前步定位、旧版结果与新的管理项；它的管理页保存全局设置时不带「每人同时进行」，服务端保持原值。
4. 分发 1.0.0 客户端。所有人装好后可以把「最低客户端版本」填成 `1000000`。
5. 建议在服务器上按 `PRODUCTION_UPDATE_GUIDE.md` 的「可选：运行真实 PostgreSQL 集成测试」一节跑一遍：这次改了复盘仓储的读写。

## 同时修复

- **手机回放页两侧栏的比例**：说明栏与控制栏原先放在牌桌画布外面，牌桌随屏幕缩小时它们不缩，手机横屏上字号与按钮比玩家框里的字大出一截，窄的左栏连标题都放不下。现在两栏和牌桌画在同一张画布里，与牌桌页两栏同一套尺寸（按钮按画布高 60 定，手机上缩到约 33 像素仍点得中）；大屏上说明在右栏上方、操作贴底。

- **对手都已全下后仍能加注**：规则引擎给出可选动作时只看这个人的加注权有没有被重新打开，没看桌上还有没有人能跟。比如一手里对手全下 3200、只剩一个筹码更深的人，他还能「加注 7980」，多出的部分在这一轮结束时退回。现在其他未弃牌的人都已全下时，`canBet`/`canRaise` 为 false，`canAllIn` 只在全下额度不超过跟注目标（也就是用全下来跟注）时为 true；服务端直接拒绝这时的加注与超额全下。客户端按服务端下发的选项显示按钮，不需要改动，旧客户端也同样生效。只要还有另一个人能行动，加注权照旧。规则见 `TEXAS_HOLDEM_RULES_V1.md` 5.1。

- 0.9.0 的 CI 在复盘仓储的 Postgres 集成测试上失败：测试样例的动作没有动作号，写入牌局时撞了主键。只是测试数据的问题，真实牌局每个动作都有唯一的动作号；已补上，并且同一套仓储检查现在也在内存实现上跑。

## 测试

- 回放页：手机横屏时两栏与牌桌同一比例缩放、按钮仍够大、标题与房间号分行显示；九人桌在七种尺寸下两栏都不压玩家框。
- 规则引擎：唯一对手全下时只能跟注或弃牌、加注与超额全下被拒、跟注后筹码正确；筹码不够跟满时仍能全下跟注；还有另一个人能行动时加注权不受影响。
- 服务端：DeepSeek 错误码的归类（含 403 只影响这一次、资源不足中途停止与只回空白按繁忙处理、超时单独归类且只重试一次）；新版分析中与失败时带着旧版结果；非 DeepSeek 地址默认不发扩展字段、`deepseek.com` 只认本域与子域；限流时两次延后重试、到点之前不领取、三次失败才记失败；余额不足时排队的一并失败、冷却期拒绝新请求、成功一次后恢复；全局与按人的每日次数、同时进行上限；按人额度的校验与「不在名单里」；旧版结果在新版没有时返回并标 `outdated`、重新分析按新版排队；两个工作协程同时分析时正在处理的都不会被误判、停机时做完再退出；请求体里的思考模式、思考强度与匿名 `user_id`（同一人稳定、不同人不同、不含账号），关掉时一个都不发；新环境变量的默认值、取值与非法值；复盘仓储的检查在内存实现与真实 Postgres（CI）上共用。
- 传输层端到端：按人额度的设置、普通玩家不能改、不在名单里被拒、名单里显示额度、记入审计。
- 客户端：重新分析被拒时旧结果照常显示、「重试」会再次发起；新版分析中或失败时下面接着显示旧版结果；单独额度的「都跟随全局」；停在本人操作过的步上打开面板会滚到并高亮那张卡片，停在别人的步上不高亮；只有旧版结果时查看不发请求、「用新版重新分析」才发；自动重试时的进度文字；管理页的单独额度（留空跟随全局、保存后按新值显示、清空回到跟随全局）与余额不足提示；新错误码都有中文。
- 用真实 DeepSeek（`deepseek-flash`、思考模式、`xhigh`、带 `user_id`）把八类牌局重新跑了一遍，全部成功。每手约 15～100 秒，输入约 2.4～3.3 千、输出约 2.5～18 千 token（含思考）。

## 已知边界

- 每人次数与同时进行上限是「先查后写」，同一个人几乎同时发起几手时可能略超；熟人规模下影响很小。
- 冷却期是进程内的，服务重启后清空；重启后的第一次调用会重新发现余额或密钥的问题。管理页的提示会区分「冷却中」与「冷却已过、等下一次调用确认」。
- 结果存库彻底失败时留下的「进行中」（极少见）在玩家对那一手点重试之前，仍占着一个「同时进行」名额。
- 分析完成时不会主动通知，要回到那手回放才看得到。
